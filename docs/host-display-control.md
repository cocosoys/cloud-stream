# 被控端显示模式控制（#89）

把被控端的**真实屏幕分辨率**改成浏览器画面区域的尺寸，让抓屏、编码、显示三者
1:1。这条链是为了消除「画面被缩小显示」带出来的连带问题，最典型的是游戏模式下
指针跟不上手。

## 1. 它解决的是什么

`r,<W>x<H>`（#50）只改**编码目标**：被控端仍然是 1920×1080 的桌面，libyuv 把它
挤进请求的缓冲区。

```
被控端桌面  1920×1080
   ↓ 抓屏（原生）
   ↓ 缩放（r 请求 1714×922）
传输帧      1714×922
   ↓ 浏览器显示在 1714×922 的框里
```

帧与框 1:1，但**帧与桌面不是 1:1**。前端在绝对定位（全屏模式）里用
`_pointerScale() = 帧宽 / CSS 宽` 把指针换算过去；相对增量（指针锁定的游戏模式）
不乘这个系数，于是一个手部动作在屏幕上只走 `1/1.12 = 0.893` 的距离 —— 慢 10.7%，
窗口越小差得越多。

`dr,<W>x<H>` 改的是被控端桌面本身：

```
被控端桌面  1714×922   ← dr 改到这里
   ↓ 抓屏（原生，无缩放）
传输帧      1714×922
   ↓
```

三条路一起变成 1:1：编码不缩放（文字锐利）、`_pointerScale()` 恒为 1（绝对定位
精确）、相对增量的缺失系数不再有影响（本来就是 1）。

## 2. 协议

浏览器 → 服务端（控制通道，与 `r,` 同一套 `classify`）：

| 消息 | 含义 |
|---|---|
| `dr,<W>x<H>` | 把被控端显示模式切到 W×H。W/H 会向下取偶（VP8 的色度行） |
| `dr,reset` | 还原到本进程首次切换之前的模式 |

服务端 → 浏览器（一条 JSON，`type` 为 `display_resolution`）：

```json
{"type":"display_resolution","requested":"1714x922","applied":"1600x900",
 "width":1600,"height":900,"exact":false,"strategy":"nearest-reported"}
```

失败时 `applied` 为 `null`，另有 `error` 字段带驱动原话。

`strategy` 取值：`already`（已经是这个尺寸）、`reported`（驱动支持的列表里有）、
`unsafe`（用 `CDS_ENABLE_UNSAFE_MODES` 让驱动接受列表外的尺寸）、
`nearest-reported`（都不行，退到不超过请求的最大支持模式）。

## 3. 三级策略与安全边界

`dispatch/display.rs`：

1. **reported** —— 请求的尺寸在 `EnumDisplaySettingsW` 的列表里，直接切。最安全。
2. **unsafe** —— 不在列表里时，用 `CDS_ENABLE_UNSAFE_MODES` 再试一次。桌面显卡
   驱动通常接受（"自定义分辨率"工具就是这么做的）。这是绝大多数情况实际走的路。
3. **nearest-reported** —— 前两者都失败，退到不超过请求的最大支持模式，并在
   回执里标 `exact: false`。

每一步都先 `CDS_TEST` 再 `ChangeDisplaySettingsW`：驱动不接受就根本不会上屏。
`CDS_TEST` 不是可选项，它是"打错一个数字就黑屏"和"打错一个数字就报错"之间唯一的
那道闸。

还原只做一次：本进程首次切换前用 `ENUM_CURRENT_SETTINGS` 记下原模式，`dr,reset`
读这个值回去。没切换过的时候 `dr,reset` 会报错而不是乱设一个尺寸 —— 一条误发的
reset 不该重排一个流从来没碰过的桌面。

## 4. 与 `r,` 的关系

`dr,` 成功后服务端会**同时**把编码目标设成实际生效的尺寸：

- 否则客户端之前发过 `r,1920x1080`（手动分辨率模式）时，真实桌面已经变成
  1714×922，请求仍是 1920，clamp 到 1714 后虽然也是 1:1，但那纯属巧合；一旦
  客户端请求更小的值就会重新引入缩放。
- 设成实际尺寸后，编码目标 = 桌面 = 1:1 是显式的，不依赖 clamp 的兜底。

`dr,` 与 `r,` 在鉴权骨架上分属两个面（`control.display` / `control.resolution`）：
重排整个桌面比改编码尺寸的影响大得多，未来的策略要能单独放行后者、拒绝前者。

## 5. 采集端如何跟上

改分辨率会让 DXGI Desktop Duplication 失效。`pipeline/mod.rs` 有两道兜底：

- 帧几何与预期不符 → `InnerOutcome::Rebuild`（日志 `frame geometry changed`）
- DXGI 返回可恢复错误 → 重建采集/编码对（`DXGI_RECOVERY_LIMIT = 3`）

重建时 `seed_native` 会读到新的桌面尺寸，编码器按新尺寸重开，客户端收到新的帧
尺寸后自动重排。

## 6. 限制

- **只处理主显示器**。`ChangeDisplaySettingsW` 传空设备名即主屏；多屏需要
  `EnumDisplayDevicesW` + `ChangeDisplaySettingsExW`，本阶段没用到。
- **inexact 时仍会有少量缩放**。驱动只支持 1600×900 而请求 1714×922 时，画面
  按 1600×900 传输、在 1714×922 的框里放大 7%，游戏模式那 7% 还会在（比原来的
  10.7% 小）。回执里的 `exact: false` 就是给用户看的。
- **会重排被控端桌面**。图标位置、最大化窗口尺寸都会跟着变。这是真实分辨率
  切换的固有代价，不是 bug。
- **Windows 会闪一下**。切换是全局的，无法避免。

## 7. 前端入口

左侧工具栏 → 屏幕 → 「强制被控端匹配本机窗口」/「恢复被控端分辨率」。

尺寸取的是**画面元素的渲染尺寸**（`Input.getStreamCssSize()`），不是
`getWindowResolution()` —— 后者是整页尺寸，含仪表盘边框，会让被控端比视频大
一圈，于是又有了缩放。
