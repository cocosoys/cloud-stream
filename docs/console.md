# 工具箱：`stream-setting.exe`

一句话：**`stream-server` 的工具箱** —— 看它现在什么状态、改它的配置、换它的版本、把它卸掉。装和卸的**流程**归安装器（Inno 的 `unins000.exe` / MSI），这里只留入口和状态。

## 1. 它是什么

一个单文件 exe（`crates/setup`，**不链接** `stream-server`）。不带 payload 时 377 KB，带 `--features embed` 时约 9 MB —— 那时它既是工具箱，也是整个安装包：双击打开就是下面这个窗口。

> 它从前叫 `cloud-setup`，再往前是"和 `install.cmd` / `uninstall.cmd` 放在同一个目录"的第三个东西。那两个脚本已经不在了，见 `docs/operations-install.md`。改名是因为它已经不再"setup"：装和卸都归安装器了，剩下的是台机器旁边那个人的日常操作 —— 看状态、改配置、换版本、卸掉。

```
┌ stream-setting · stream-server 的工具箱 ────────────┐
│ 程序信息                                            │
│ ┌─────────────────────────────────────────────────┐ │
│ │ 服务      运行中（pid 4120）                     │ │
│ │ 端口      8080 · 正在监听                        │ │
│ │ 看门狗    MCStreamSrv · 已注册                   │ │
│ │ 目录      C:\Program Files\cloud-stream          │ │
│ │                                                 │ │
│ │ -- 服务端自述（--ops state）--                   │ │
│ │ root:      C:\Program Files\cloud-stream         │ │
│ │ version:   0.4.0 (eb908d6)                      │ │
│ └─────────────────────────────────────────────────┘ │
│ [刷新状态]    [更新]    [卸载]    [改配置]           │
│ 操作记录                                            │
│ ┌─────────────────────────────────────────────────┐ │
│ │ -- 状态已刷新                                    │ │
│ └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

上面那三行（服务 / 端口 / 看门狗）是**窗口自己查的**，不依赖服务端配合：

* 进程按**完整路径**枚举 —— 同一台机器上可能还有另一个目录的安装，任务管理器里两个 `stream-server.exe` 长得一模一样；
* 端口从配置里读（`effective_config`），所以 `cloud-stream 9000` 那种改过端口的机器不会显示"没有应答"；
* 看门狗直接读 `%SystemRoot%\System32\Tasks\MCStreamSrv`，顺带能分辨"已注册但被禁用"。

`--ops state` 的原文接在下面：它回答的是"配置和快照是什么样"。服务起不来的时候它也可能失败，所以那三行不能指望它。

窗口打开的那一刻就会跑一次，所以"这台机器现在是什么状态"不用点任何按钮就在上面。

## 2. 四个按钮落到哪

| 按钮 | 实际执行 | 需要管理员 |
|---|---|---|
| 刷新状态 | 自己查进程/端口/任务 + `stream-server.exe --ops state` | 否 |
| 更新 | 先 `--update check`；有新版就确认，再 `--update apply` | 否 |
| 卸载 | 先确认，再 `runas` 拉起同目录的 `unins000.exe`，成功后本窗口立刻销毁自己 | 是 |
| 改配置 | 打开配置表单（见下一节）；保存时 `--ops config-set` | 否 |

**没有第二个实现。** 窗口里能做的，命令行里都能做；命令行里能做的，窗口里也能做。这一点是刻意的：一旦界面自己写一套"顺手"的删除/覆盖逻辑，两条路径就开始各自漂移，而漂移出来的差别只会在出故障那天被发现。

**为什么卸不下来的按钮少了三个。** 「拍快照」「回滚」「安装 / 修复」都删了：前两个是 `stream-server.exe --ops snapshot|rollback` 的入口，那件事属于服务端自己的运维（`docs/operations-rollback.md`），不该在"工具箱"里占一排按钮；「安装 / 修复」则是安装器的本职 —— 从窗口里重装一遍，等于让一个窗口去驱动提权安装，而安装器本来就带着自己的完整性检查。

**「卸载」为什么不自己调 `--uninstall`。** 因为那会让"卸载要做哪几步"有两份定义（一份在 `uninstall.rs`，一份在 uninstaller），而两份迟早分叉 —— 最先分叉的会是"配置要不要先备份"这种判断。现在窗口只负责把 `unins000.exe` 叫起来；它按自己的顺序逐条调后端的五个单步命令（`--uninstall-step`），每条都进 Setup 日志。目录里没有 `unins000.exe`（便携包直接解出来的）时，按钮会说清楚"删掉整个目录即可"，而不是假装能卸。

**窗口为什么自己也该死。** 从按钮点的这条路，窗口在拉起卸载器之后就销毁了；但从**控制面板 /「应用和功能」**点的卸载绕不过这个问题：`{app}\stream-setting.exe` 还开着，而 `{app}` 里正在执行的 exe 删不掉（影像段不带 `FILE_SHARE_DELETE`）—— Inno 会记一句 `Failed to delete directory (32). Will retry later.` 然后把目录留在那儿，ARP 清空、任务没了、规则也清了，只留下一个装着 `unins000.exe` 的空目录。所以第 2 步（`procs`）现在把同目录下的控制台一起收掉（**不含自己**，否则这一步会把自己杀了，后面三步没人做）。`.150` 上就是这么漏的：一个 09:06 双击开的旧 `cloud-setup.exe` 窗口挂了两小时，卸载只剩下一个空目录。

## 3. 起不来的时候：`--diagnose`

「程序信息」那三行回答的是"现在是什么状态"，回答不了"为什么起不来"。后者归
`stream-server.exe --diagnose`：九节事实一次写成 `cloud-stream-facts.txt`
（运行根 + 桌面各一份），只读、不启动服务、不改任何东西。两个 exe 都认这个
开关 —— `stream-setting.exe --diagnose` 会转调过去，因为两个 exe 躺在同一个
目录里，敲错名字是常态。

它替掉了 `collect-launch-facts.cmd`（184 行 cmd）。那个脚本存在的唯一理由是
"exe 起不来的时候谁来收现场"，而 exe 起不来的头号原因是缺 VC++ 运行时；现在
`vcruntime140.dll` 跟着包走（app-local 部署），那个失败模式消失了，脚本也就
没有存在理由了。

九节的顺序与旧脚本一致（会话 / 账户策略 / 包内容 / 加载器前提 / 运行状态 /
日志尾部 / 任务计划事件 / Defender / 入站可达性），所以文档里"看第 9 节"这类
说法继续有效。第 5 节会**排除自己**：诊断进程的映像名也叫 `stream-server.exe`，
把它列进"在跑的实例"正好把这一节要回答的问题答反。

## 4. 配置表单

「改配置」以前是拿记事本打开 TOML。那条路的失败代价太高：拼错一个键名，服务**下次启动**才失败，而那一刻人已经离开了 —— 屏幕上是黑的，日志在下一个能起来的版本里。

现在是一个表单（另一个窗口，`stream-setting.exe --config` 也能直接打开它）：

```
┌ 配置（改完要重启服务才生效） ──────────────────────┐
│ 端口                画面宽                          │
│ [8080          ]    [1920          ]                │
│ 画面高              帧率                            │
│ [1080          ]    [15            ]                │
│ 视频编码            传输模式                        │
│ [vp9         ▾]     [             ▾]                │
│ ...（两列共 19 格）                                 │
│ 访问口令                                            │
│ [••••••••      ]                                    │
│ [保存] [重新读] [打开原文]                          │
└─────────────────────────────────────────────────────┘
```

* **格子由服务端的类型表决定。** `--ops config-get --ops-json` 给出每个键的类型、范围、枚举选项和**文件里写着的那一行**。枚举与布尔是下拉框（`CBS_DROPDOWNLIST`），整数与路径是文本框，口令是密码框（`ES_PASSWORD`）。
* **界面不判断值合不合法**，也不写文件。保存只是把**改过的**那几格拼成 `--ops config-set`，校验、留底、原子写、改完复查都在那一条命令里。
* **留空 = 删掉这一行 = 用默认值。** 下拉框不选（`CB_SETCURSEL(-1)`）同理。这正是"空串"与"没有这一行"的区别，文件语法里说不清，表单里一格空着就说清了。
* **口令那一格打码**，而且 `--ops config-get` 的文本输出里只显示"（已设置）"—— 这块屏幕常常正被远程看着（这软件本身就是干这个的），明文口令出现在别人的画面上是实打实的泄露。它还支持任意字符（含引号、反斜杠、中文）：写进 TOML 之前会做转义，不再是 cmd 时代那个"只限 ASCII"。
* 保存成功后回读一遍，把服务端规范化过的值显示出来（输入 `VP9` 会变成 `vp9`）；**失败时不回读** —— 人刚打的字还在格子里，覆掉之后既看不见自己写了什么，也不知道该改哪儿。
* 「打开原文」是逃生口：表单覆盖常见的十几项，`auth_grants`（多租户令牌表）、证书路径这些还是得开记事本。表单不假装自己覆盖全部。

## 5. 三个刻意的取舍

**不用 Tauri / egui。** 这个窗口要画的东西是四个按钮和两块文本。Tauri 会拖进一个运行时和四百个 crate；`windows-sys` 已经在依赖树里（服务端用它做采集与输入），`serde_json` 也已经为了读 `--ops config-get --ops-json` 编过一次，所以增量成本接近零、两秒构建。代价是界面语言是 Win32 而不是 CSS —— 对这个尺寸，这笔账划算。真要复杂界面，再换不迟，按钮背后的命令不用动。

**不链接 `stream-server`。** 壳只做三件事：起子进程、读输出、画窗口。于是它不会把 30 MB 的推流依赖（webrtc / scrap / opus）拖进一个按钮窗口，也不会因为服务端某次重构编译不过。

**提权那一段的输出，本窗口一个字都收不到。** 这是个 GUI 子系统的进程（`windows_subsystem = "windows"`），本身没有控制台；`runas` / 自己重启成管理员之后的那份进程，stdout 同样去了一个没人看的 NUL。与其假装抓到了再显示一半，不如让结论走文件：安装写 `%ProgramData%\cloud-stream\last-install.txt`，本窗口盯着它，读到带 `=== RESULT:` 的那一份就整段贴回日志面板。

卸载也写同一个文件，但是两段式：动手之前先落 `PENDING (目录由替身删除)`，替身删完目录之后自己再补一行 `UNINSTALLED`。原因是卸载最后连目录带日志一起删了 —— 等它结束时，机器上唯一还能回答"上一回卸干净了吗"的就只剩这份放在 `ProgramData` 里的文本。代价是本窗口在赶卸载的那一刻就得关掉（`DestroyWindow`），所以这两行没人替它显示，等下次双击安装器时用 `--plan` 或直接开文件看。

所有动作都在后台线程执行：安装要等最多 60 秒探活，同步跑会让窗口"未响应"，而一个未响应的窗口看起来就是崩了。

## 6. 高分屏（Per-Monitor DPI）

三步，缺一不可：

1. **清单里声明 PerMonitorV2**（`crates/setup/stream-setting.manifest`，由 `build.rs` 用
   `/MANIFEST:EMBED` 嵌进 exe）。这一条只能在清单里写：进程启动那一刻系统就按它决定
   "要不要替这个进程做位图缩放"，而同一个进程只认第一次设置 —— 事后调
   `SetProcessDpiAwareness` 改不回来。
2. **尺寸按 DPI 换算**：布局写成一张 96 DPI 的表（`MAIN_LAYOUT`），创建控件时先给 0
   尺寸，再由 `apply_main_layout` / `apply_config_layout` 按 `GetDpiForWindow` 算一遍。
   字体同理，按 DPI 建、旧的 `DeleteObject` 掉。
3. **`WM_DPICHANGED`**：窗口被拖到另一块不同缩放的屏上时，系统给一个"按新 DPI 算好的
   矩形"，照它摆 `SetWindowPos`，再按新 DPI 重排控件。只改窗口不重排 → 控件挤左上角；
   只重排不改窗口 → 控件溢出。

两个刻意的细节：

* **缩放用四舍五入**（`(value * dpi + 48) / 96`）而不是截断。125% 下 100 该是 125；
  截断得 124，单个控件差 1px 看不出来，一列排下来就是可见的错位，而且只有高分屏才复现。
* **窗口初始尺寸按 `GetDpiForSystem` 算**，不能指望 `WM_DPICHANGED` 补救：创建窗口
  时不会有那条消息。

## 7. 踩过的坑

**Win32 的 EDIT 控件不把裸 `\n` 当换行。** `--ops state` 走 Rust 的 `println!`，输出裸 `\n`；第一次跑起来，状态框里七行全挤成一行 —— 而且看起来像"输出格式坏了"，实际是控件语义。现在 `set_state` 会归一化成 `\r\n`。

**`/MANIFESTINPUT` 的路径不能带引号。** 第一版写了 `"{}"` 想保护带空格的路径，结果
rustc 把引号原样带进链接命令行，link.exe 去找一个名字里真带引号的文件，报 `LNK1104`
—— 看起来像"文件不存在"，其实是引号成了文件名的一部分。现在不加引号（代价：仓库路径
不能有空格，有的话是链接失败，而不是悄悄丢掉清单）。

**「没有改动」不是失败。** 第一版点保存时只要没改任何格子就弹"没有存成功"，理由是那句提示的行文里没有 `[exit 0]`。现在 `submit_config` 明确返回"是否真的成功"，没改动算成功。

**跨进程改不了别的窗口里的控件。** 验证表单时用一个小程序发窗口消息，`SetWindowTextW` / `GetWindowTextW` 对**另一个进程**里的控件一律无效（前者返回 0，后者返回空），必须用 `WM_SETTEXT` / `WM_GETTEXT` 让系统编组。这不是控制台的 bug，但"用脚本驱动界面自测"这件事会在这里静默失败 —— 第一次就是这么被骗的：控件没改成，保存报了"没有改动"，我还以为是保存逻辑坏了。

**`config.toml` 与 `stream-config.toml` 不是同一个名字。** `--ops state` 原本只报 `config.toml (absent)`，而整包分发的那份叫 `stream-config.toml`、由 `--run` 用 `--config` 显式指定 —— 于是屏幕上写着"没有配置文件"，实际上文件就在旁边、服务正在用它。现在 `state` 在默认位置不存在时会再看一眼同目录的 `stream-config.toml`。刻意**没有**改 `configfile::default_path`：那是启动时的自动发现逻辑，动它等于改变已有部署的加载行为。
