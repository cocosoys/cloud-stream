# 可视化控制台：`cloud-setup.exe`

四动作差距矩阵里，「可视化界面」这一列原本四格全红 —— 安装和卸载只有 cmd 黑框、更新要开发机、修改是文本编辑器。这个窗口就是那一列。

## 1. 它是什么

一个 372 KB 的单文件 exe（`crates/setup`，**不链接** `stream-server`），和 `install.cmd` / `uninstall.cmd` 放在同一个目录，双击打开：

```
┌ cloud-stream 控制台 ────────────────────────────┐
│ 程序文件                                        │
│ ┌─────────────────────────────────────────────┐ │
│ │ root:      C:\dev\stream                     │ │
│ │ version:   0.3.0 (eb908d6)                   │ │
│ │ backups:   C:\dev\stream\state\backups       │ │
│ │ rollback:  20261110T081849Z-before-change    │ │
│ │ snapshots: 2 (含自动留底)                    │ │
│ │ config:    ...\stream-config.toml (present)  │ │
│ └─────────────────────────────────────────────┘ │
│ [刷新状态] [拍快照] [回滚] [安装/修复] [卸载] [改配置] │
│ 操作记录                                        │
│ ┌─────────────────────────────────────────────┐ │
│ │ -- 状态已刷新                                │ │
│ └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
```

窗口打开的那一刻就会跑一次 `--ops state`，所以"这台机器现在是什么状态"不用点任何按钮就在上面。

## 2. 七个按钮落到哪

| 按钮 | 实际执行 | 需要管理员 |
|---|---|---|
| 刷新状态 | `stream-server.exe --ops state` | 否 |
| 拍快照 | `--ops snapshot --ops-label manual` | 否 |
| 回滚 | 先确认，再 `--ops rollback` | 否 |
| 更新 | 先 `--update check`；有新版就确认，再 `--update apply` | 否 |
| 安装 / 修复 | `cmd /c install.cmd /y`，`runas` 拉起 | 是 |
| 卸载 | 先确认，再 `cmd /c uninstall.cmd /y`，`runas` 拉起 | 是 |
| 改配置 | 先 `--ops snapshot --ops-label preedit --ops-paths stream-config.toml`，再用记事本打开 | 否 |

**没有第二个实现。** 窗口里能做的，命令行里都能做；命令行里能做的，窗口里也能做。这一点是刻意的：一旦界面自己写一套"顺手"的删除/覆盖逻辑，两条路径就开始各自漂移，而漂移出来的差别只会在出故障那天被发现。

## 3. 三个刻意的取舍

**不用 Tauri / egui。** 这个窗口要画的东西是七个按钮和两块文本。Tauri 会拖进一个运行时和四百个 crate；`windows-sys` 已经在依赖树里（服务端用它做采集与输入），所以增量成本是零个新依赖、两秒构建。代价是界面语言是 Win32 而不是 CSS —— 对这个尺寸，这笔账划算。真要复杂界面，再换不迟，按钮背后的命令不用动。

**不链接 `stream-server`。** 壳只做三件事：起子进程、读输出、画窗口。于是它不会把 30 MB 的推流依赖（webrtc / scrap / opus）拖进一个按钮窗口，也不会因为服务端某次重构编译不过。

**提权的两个动作在新窗口里跑。** 用 `runas` 拉起时 `install.cmd` 的输出在新开的控制台里，本窗口抓不到。与其假装抓到了再显示一半，不如明说"已在新窗口运行，以那个窗口的 [ok]/[fail] 为准"。等这两个脚本哪天能往 `%TEMP%` 写一份结果文件，再把输出接回来 —— 那是一个独立的小改动，不需要动这里的架构。

所有动作都在后台线程执行：`install.cmd` 要等最多 60 秒探活，同步跑会让窗口"未响应"，而一个未响应的窗口看起来就是崩了。

## 4. 踩过的坑

**Win32 的 EDIT 控件不把裸 `\n` 当换行。** `--ops state` 走 Rust 的 `println!`，输出裸 `\n`；第一次跑起来，状态框里七行全挤成一行 —— 而且看起来像"输出格式坏了"，实际是控件语义。现在 `set_state` 会归一化成 `\r\n`。

**`config.toml` 与 `stream-config.toml` 不是同一个名字。** `--ops state` 原本只报 `config.toml (absent)`，而整包分发的那份叫 `stream-config.toml`、由 `start-stream.cmd --config` 显式指定 —— 于是屏幕上写着"没有配置文件"，实际上文件就在旁边、服务正在用它。现在 `state` 在默认位置不存在时会再看一眼同目录的 `stream-config.toml`。刻意**没有**改 `configfile::default_path`：那是启动时的自动发现逻辑，动它等于改变已有部署的加载行为。

## 5. 状态

| 项 | 状态 |
|---|---|
| 构建 | `toolchain/build.ps1 -Task build -Package cloud-setup`，2 秒 |
| 体积 | 372 KB（debug） |
| 已验证 | 窗口能起、状态面板七行正确、七个按钮布局不重叠、静置 16 秒不会自己触发动作 |
| 未验证 | 真机上点"安装/卸载"（需要管理员，且 `.150` 离线）；DPI 缩放下的观感（没做 Per-Monitor DPI，高分屏上会略糊） |

下一步该补的三件事，按价值排序：把 `install.cmd` 的结论写进 `%TEMP%` 再读回来（于是提权动作也能在本窗口显示结果）；加一个配置表单替代记事本；Per-Monitor DPI。
