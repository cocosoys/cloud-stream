# 2026-11-06 — SOYSHTTPOverMC / cloud-stream

## #113 换传输之后指针不响应：输入租约锁在旧传输上

用户报："从 WebSocket 切回 WebRTC 又黑屏，且 WS 实现的指针不是和 WebRTC 一样的
交互效果，体感上认为是再次渲染上去的，导致悬停/交互没有任何反馈。"

### 黑屏

上一轮的 `PREFERRED_CODEC`（进程级编码器记忆）+ PLI 自适应去抖已生效，本次复查
无重启环：`codec vp8 / pli 0 / encode_ms 7.8 / reconnects 1`（那 1 次是部署重启）。

### 指针（真因）

服务端日志一次说清：

```
session 2 (signaling/WebRTC) → pipeline 0: input lease None -> Some(2)
ws media … attached as session 3 → grant=viewer operates=yes lease=no
#103: input lease moved to session 3 over HTTP (was Some(2))
ws media … attached as session 4 → lease=no
session 3 unregistered → input lease handed to session 2 (holder left)
session 5 … attached → lease=no
```

`exclusive` 下租约是**永久所有权**（claim-if-free、没人能挤掉、只在收尾归还）。
页面换传输之后，旧传输的会话既活着（PeerConnection 没拆、sink 还在收字节）又再也
不投输入 —— 它把指针锁死，新的 media 连接每一条 `m,` 都被门禁丢掉。页面上表现成
"指针跟着鼠标动、桌面一动不动"（指针是浏览器自己画的），且重连治不好。

三层修法：
1. `SharedPipeline::input_at`（`Mutex<Option<Instant>>`）+ `note_input()`，
   只在**真注入点**盖章（WS 的 `Action::InputStub`、WebRTC 指针通道）——门禁也被
   `pong`/`SETTINGS` 问，在那里盖章会让死会话永远"在用"。
2. 租约失效：`LEASE_ADOPT_IDLE = 1.5s`（落座时 `adopt_lease_if_stale`）、
   `LEASE_TAKEOVER_IDLE = 3s`（每条真输入时的 `may_inject` 兜底）。
   `input_idle() == None`（认领过但从未输入）**与陈旧同义**，否则两条都不注入的
   连接会各握半边锁互等。接管后立刻盖时间戳，否则每条消息换一次主人、各丢一半。
3. `may_inject(session, may_operate, is_input)` —— 只有真输入能触发接管，控制类
   指令不驱动指针，不该有资格说"我在用"。
4. `successor()` 排序改成 **先看有没有下行（sink），再看新旧**：原来取"最老的"，
   而换传输后最老的恰恰是被抛弃的那条传输。
5. 诊断栏：`ws media: … lease=yes|no prev_idle=never|N.Ns` —— 只看 `lease=no`
   分不清"悬空租约"与"正常两页签"，而两者处置完全相反。

  帧号 / 60 帧 / 1920x1080**，说明线上帧率与帧号都没有问题。

  里的 `window.fps` / `window.videoChunksReceived` / `window.stream_stats`。绕过了

  canvas 绘制点三处，任一处没接上就整场为 0，而画面正常。

  `takeStreamSample`）：这一秒没有呈现证据时报 `window.fps` 而不是 0；`videoWatch`
  缺失时补绑。已构建部署（core `selkies-core-B5PSJB--.js`，服务未重启）。
  注意：**构建根是 `~/Desktop/selkies-webclient`**，不是 `~/Desktop/selkies-gstreamer`；
  后者也同步改了同一处，避免两份源码分叉。
- 测试副作用：无头页把输出分辨率改成了 756x488，用户强刷后页面会重新设为 1920x1080。

## #115 "操作桌面后 FPS 从 60 一路跌到 0，然后 0/1 浮动"

实测（工具都在 `toolchain/`）：
- `ws-fps-probe.py` 直连：静止桌面 **60 个不同帧号/秒**，连续三次稳定 → 帧没断。
- `page-probe.py` / `fps-watch.py`（无头 756x488、窗口化 1920x1080）：静止、右键、
  拖动框选、持续移动光标，客户端 `window.fps` 全程 55-61，`outAge` < 30ms → 页面统计也没断。
- `stop-verify.py` **决定性**：同一条连接发 `STOP_VIDEO` 前 180 帧/3s，发后 **0 帧/3s**，
  `START_VIDEO` 后再恢复。所以服务端"停了这条连接"与"编码器仍 60"可以同时成立 ——
  面板的「服务器 FPS」是编码口径（new+repeat），不含"这条连接收到没有"。
- 服务端日志（scp `C:/dev/stream/logs/stream-server.log` 到本地 grep）：用户会话
  出现 `STOP_VIDEO` → `START_VIDEO` → `STOP_VIDEO`，**此后十几分钟没有 START**；
  同期 `pipeline 5.0s: loop=60.0Hz` 一直满速。这就是"服务端 60 / 客户端 0/1"的画像。
- 前端停视频的唯一入口是 `visibilitychange → hidden`（250 ms 防抖后 `pauseVideoForHiddenTab`）。
  恢复要求 `videoPausedForHiddenTab` 为真 **且** socket 处于 OPEN **且** 收到 visible；
  缺一项就永久停住（`resumeCarriedPipelines` 只对用户手动关闭的管线补发）。
- 另一个候选机制（已确证逻辑但未在线上触发）：`ws_media.rs` 的 `dropped` 是**整条连接的
  累计数**，却被用来判断"下一帧要不要等关键帧"（`if dropped > 0 && !need_key`）。
  一旦排空过一次队列，从此每一拍都会重新置 `need_key`，只剩 10 s 一次的周期 IDR 能过闸
  → 恰好是 0/1 浮动。停读 2 s 的复现实验没压满 TCP 缓冲，所以线上未复现，但代码是隐患。
- 另见整机资源饥饿：日志里出现过 `loop=0.1~13Hz`、`enc_avg=340ms`、`conv=2626ms`
  （1080p VP9 软编在 4 核 VM 上被抢 CPU），那段时间帧率是真的掉到 0。
- 线上包已确认包含 #114 的修复（`assets/selkies-core-B5PSJB--.js` 里
  `fps:!(r>0)||s===0?window.fps:...`），所以"0"不是旧包的锅。
- 新增工具：`page_probe_lib.py`（CDP 公共库）、`fps-watch.py`、`desktop-act.py`
  （右键/拖动/移动，动作经页面真实输入链）、`stop-verify.py`、`drop-verify.py`。

## #116 "操作桌面后客户端 FPS 从 60 跌到 0/1 并停住" —— 真根因

用户回传控制台：[60, 1520, 'visible'] → [0, 2902, 'visible'] → 2904，中间夹着
`Tab hidden → STOP_VIDEO → visible → START_VIDEO`。

排查（每步都实测，避免又一次"改错副本"）：
1. 服务端是否还在发：`/api/v1/health` 里该会话 `frames_total` 每秒 +60、每帧约
   1.2 KB；`ws-fps-probe.py` 直连每秒 60 个不同帧号。→ 帧在发。
2. 前端计数分支：把线上 bundle 下载下来按 `videoChunksReceived` 定位，确认与源码
   一致（`0x04` 分支的 `uniqueStripedFrameIdsThisPeriod.add` 在所有 return 之前）。
3. 实测 `AUTH_SUCCESS` 为 `role=controller` → `isSharedMode` 不成立，排除。
4. 页面上 `divert=false`、`rows=0`、`size=1576x808` → 走页面路径，不是 worker、
   不是条纹。`hidden-cycle.py`（切走 15 秒再切回）只能复现"切回后 1-2 秒 0"，
   随后必然恢复 —— 所以用户的持续 0 不是可见性本身。
5. 决定性一步：`fanout.rs:338` 的 `counters.frames/bytes` 在 `try_send` **入队
   成功**时就 +1。health 那两个数都是"入队"，不是"发到 wire"。
6. 下行循环 `ws_media.rs`：`dropped` 声明在 loop 外（累计），却用来判断
   `if dropped > 0 && need_key == false { need_key = true }` —— 排空过一次队列就
   永久上闸，只有每 10 秒一个的 IDR 能过。60 → 0.1 帧/秒 → 面板 0，偶尔 1。
   **"0 和 1 之间浮动"就是这个取整。**

修复：
- `key_gate_after_batch(queued, need_key)`：闸只看这一批；上闸瞬间
  `request_keyframe()`，真实丢帧仍等关键帧但不该等 10 秒。
- 前端：`window.fps` 分母改成按**帧到达时刻**算（`noteWireArrival` /
  `wireArrivalRate(spanMs)`，分子分母同源）；`sendClientMetrics` 在帧到达路径上
  兜底调用（定时器被降频或清掉也不会冻住读数）；报 0 而这一拍有分块时打一行
  `[fps] reported 0 but N video chunks arrived ...(shared= mode= divert= ids=)`。
- 单测：`one_skipped_batch_does_not_gate_the_stream_forever`、
  `a_steady_one_frame_per_beat_never_gates`（`cargo test -p stream-server ws_media`
  19 passed）。本机 cargo 要从不被 Git Bash 的 `link` 抢走 `link.exe` 的环境跑。
- 回归工具 `toolchain/gate-latch.py`：停读 2 秒制造真实背压，修复后实测恢复第 1
  秒 181 帧、之后稳定 59-63 帧/秒。
- 已部署：backend pid 10552，前端 core `selkies-core-CfcJO7sq.js`。

未做但值得做：health 的 `frames_total`/`avg_mbps` 其实叫"入队"，容易被当成
"已发送"；应加一个真正 `sink.send` 成功之后才 +1 的 `sent_frames`，这样"连接还在
但被闸住"一条 curl 就能看出来。

## #117 默认值改成 WebSockets + VP9

需求：串流模式默认 websockets，编码器默认 VP9。

三层各一处（漏一层就表现为"默认没变"）：
- 服务端 `config.rs`：`default_mode` webrtc→websockets、`video_codec` vp8→vp9；
  启动脚本没写这两个旗标，所以改代码默认值即生效。
- 面板 `Sidebar.jsx`：`DEFAULT_ENCODER = encoderOptions[0]`（=h264enc）→ `"vp9enc"`。
  注意 `server_settings.encoder.value` 回显的是**正在跑**的编码器且优先级高于本地
  存储（#94），只改面板会被服务端覆盖回去。
- 前端核心 `selkies-ws-core.js` / `selkies-wr-core.js`：`getStringParam('encoder',
  'h264enc')` → `'vp9enc'`（`server_settings` 到达前的本地记账）。

单测：`config::websockets_and_vp9_are_the_first_load_defaults`（新），
`pipeline::shared` 两条原先断言"CLI 默认 vp8"的用例按新默认翻转
（`shared::` 19 passed，`config::` 9 passed）。

验证：`toolchain/defaults-probe.py` —— 一次性 profile 起无头 Edge，展开"视频设置"
后读 DOM：storedMode=websockets、panelMode=websockets、panelEncoder=vp9enc、
transport=1(OPEN)；`/api/status` current_mode=websockets；health `stream.codec=vp9`；
`ws-fps-probe.py` 稳态 60 帧号/秒。

已部署：后端 pid 7528，前端 core `selkies-core-DIA5mzHS.js`。
