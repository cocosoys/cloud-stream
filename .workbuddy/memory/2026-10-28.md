## #72 游戏模式指针不动：真因是服务端没读 `pointer` 数据通道（已修/已部署）

- 用户实测反馈（1920x1080 改造后）：铺满 OK、退出 OK、点击精度 OK、无双光标，
  但游戏模式里指针仍不动。浏览器控制台刷屏不再有 `server-enforced`，但服务端
  日志仍有 `SETTINGS: manual resolution -> 1920x1080`（客户端 localStorage 残留）。
- **服务端日志实证**（拉回本地 `dump-triage/srvlog/stream-server.log` 分析）：
  - `capture source opened: 1718x926` —— 被控机桌面**仍是 1718x926**，用户改的
    1920x1080 没落地。注册表 `HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers\Configuration`
    下 VMware 键（`NOEDID_15AD_0405...`）的 `ActiveSize.cx/cy` = 0x6b6/0x39e = 1718x926，
    说明是 VMware SVGA（15AD:0405）+ 自动适应客户机，改完又被拉回。
  - 指针窗口：`paint=1 on=true m2=3 dm=0` → 5 秒内只 3 条相对增量且注入 0 像素。
- **真因（不是坐标，是通道）**：
  - 前端 `Input._sendPointer(fields, motion)`：`motion=true` 走
    `webrtc.sendMotionMessage`（selkies-wr-core.js:3189），只要 `pointer` 通道 open
    就发到该通道（webrtc.js:898）。键盘/滚轮/鼠标按键是 `motion=false`，走 `control`。
  - 服务端 `ControlChannels::open()` 建了 `pointer`，但**只有 `control` 绑了
    `on_message`**。webrtc-rs 的 `read_loop` 是
    `if let Some(handler) = &*on_message_handler.load() {...}`（webrtc/src/data_channel/mod.rs:374）
    —— 没有 handler 就是**读完直接丢**。所以每条 `m`/`m2` 都被扔掉。
  - 这解释了「键盘好、点击准、指针不动」：按下事件走 `control` 所以落点准，
    连续移动全在 pointer 通道上，全丢。
- **改法**：`ControlChannels::pointer()` 访问器 + `websession` 给 pointer 绑
  `on_message`（只接受 `Action::InputStub`）；`WinInputSink.last_abs_seq` 用前端
  已有的 `_pointerSeq` 丢弃无序通道上过期的绝对 `m`（只过滤 `m`，`m2` 是增量可交换，
  不能丢）。5s 统计行新增 `m=`。
- **验证信号**：窗口模式移动鼠标 → `m=` 必须增长（证明通道被读到）；游戏模式 →
  `m2`/`dm`/`paint` 必须同步增长。
- 提交 `bd5cf0e`；部署 148，远端 MD5 `c192b7ca07f187206e0aa0da296d49c1` 与本地一致；
  旧 exe 备份 `target/release/stream-server.exe.bak72`。
- **环境坑（重要）**：本会话 Bash 的 PATH 被收窄到
  `...shim/safe-bin;...node;...;C:\WINDOWS\System32;C:\WINDOWS`，`ssh`/`cargo`/`link.exe`
  都不在 PATH。做法：
  - `ssh`/`scp` 用 bash 的 `/usr/bin/ssh`（PowerShell 里 `& "C:\Windows\System32\OpenSSH\ssh.exe"`
    会报「无法在管道中间运行文档」）。
  - bash 里若把 `$PATH` 追加 MSVC 的 bin，git-bash 的 `/usr/bin/link` 会抢在
    `link.exe` 前面 → `link: extra operand`。必须把 MSVC bin **前置**才能编译。
  - 从 bash 调 `powershell` 会被安全策略拦（「Invoking PowerShell from Bash」），
    远端查询改用 `reg query` / `certutil` / `dir` 这类 cmd 命令。
  - 远端 ssh 输出夹杂二进制/NUL，管道前加 `tr -d '\000\r'` + `grep -a`。
- **未结**：被控机桌面 1718x926 无法靠客户端解决，用户需关掉 VMware 的自动适应
  或把虚拟机窗口调到 1920x1080；手动分辨率需点「重置为窗口大小」清掉 localStorage。

## #74 视角灵敏度爆表：真因是被控机指针加速曲线 × delta 合并

- **实测证据**：服务端统计行 `m2=1160 dm=11077` → **9.55 px/条**；
  被控机 `HKCU\Control Panel\Mouse`: `MouseSpeed=1, Threshold1=6, Threshold2=10, MouseSensitivity=10`。
  9.55 正落在 Windows 加速曲线的 **×2 段**（≤6 不加速，6~10 ×2，>10 ×4）。
- **机制**：加速曲线判定的是「单次 delta 大小」而非总速度。本地玩时 125~1000Hz 上报，
  每帧只有 1~2 counts → 永远在 1:1 段；串流时 `MOTION_SEND_INTERVAL_MS` 把 8ms 合并成一条
  → 单条 ~10 counts → 直接踩进 ×2/×4。同样物理速度，串流被放大 2~4 倍。
- **排除项**：前端 `_requestPointerLock` 已用 `{unadjustedMovement:true}`（input.js:5223），
  浏览器层加速已消除；`frame==screen` 使服务端倍数本来 =1.0。所以只剩 host 侧那一层。
- **业内做法**：Moonlight/Sunshine 相对移动走 kernel HID（绕过 SendInput 与加速曲线），
  Parsec 用 parsecvusba 虚拟 HID；GeForce NOW/Stadia 用 `unadjustedMovement`。
  Sunshine 文档明写 relative movement 走真实 HID 设备。
- **A（host，已生效）**：`start-mc.ps1` 薄壳在启动游戏前 `Set-ItemProperty` 三个值
  + `SystemParametersInfo(SPI_SETMOUSE=0x0004, pvParam=[t1,t2,accel])` 立即生效。
  两个关键点：加速是**按用户**的（HKCU），SSH 登录的是 user 而游戏跑在 Administrator，
  所以必须在这个以 Administrator 运行的薄壳里做，而不是从 SSH 改。
  日志 `C:\dev\mc\mouse-accel.log`：`before speed=1 t1=6 t2=10` → `SPI returned True`。
- **B（已部署）**：前端 `_relativeToServer` 不再乘 `_streamBox()` 缩放，改为 `pointerGain`（默认 1）；
  服务端 `frame_to_screen_delta` 直通。绝对定位 `frame_to_screen` 一行未动。
- **C**：`setPointerGain` 存 `localStorage['selkies-pointer-gain']`，Sidebar 屏幕区块加
  20%~200% 滑块（`pointerGainSlider`）。
- **前端构建链（重要）**：`addons/selkies-dashboard` 的 `copy-core.js` 从

## #75 指针延迟诊断 + 默认灵敏度固化（MC 0.5 / gain 1.0）

- **用户真实体感不是灵敏度，是延迟**：「鼠标已停止转动，视角仍在继续转」。这条描述
  改变了整个方向 —— 灵敏度调参治不了它。
- **关键证据 1：`m2=0 dm=0`，只有 `m=` 在涨**。前端 `input.js:2964` 的分叉是
  `_isStreamLocked()` → `m2`(相对/pointer 通道) else `m`(绝对/control 通道)。
  `_armPointerLock` 前置条件 = `inputAttached && gamingMode && document.fullscreenElement`。
  所以那两次会话里指针从未锁定 → 绝对模式 → 每次移动是「设一个目标位置」，
  控制通道可靠有序，积压时会**逐条重放历史位置**，正是「停手后还在转」。
- **关键证据 2：被控机渲染是 `SVGA3D; LLVM` + `Mesa 24.1.0`**（VMware 虚拟 GL，

## #75 补充：默认灵敏度改为数据推导值 0.5（网络数据加权）

- 用户要求「用网络玩家数据找出最合适默认值」。搜到的硬数据：
  - **DPI 分布**（senslab.pro，999 名验证 FPS 选手，2026-10-04）：800=523 人(52%)、
    1600=242(24%)、400=165(17%)、3200=19(2%)、1200=15(2%)、1000=7(1%)。
    dcprosens 2026 社区调查给出 800/400/1600 = 44%/32%/11%，800 都第一。
  - **MC 灵敏度分布**（Hypixel 论坛投票 105 票，2021）：≤49% 25.7%、50-79% **37.1%**、
    80-99% 14.3%、100-119% 18.1%、120%+ 4.8%。中位 ≈65%，加权均值 ≈75%。
    同帖具体配置：70%@800、69%@800、45%@800、55%@1200、60%@600、24%@1400。
    中文教程普遍建议 60%。
- **换算**（MC 1.12.2 `EntityPlayerSP.onUpdate`）：`deg/count = 1.2*(0.6s+0.2)^3`，
  `cm/360 = 360/deg_per_count/DPI*2.54`。样本换算后 MC 玩家实际在 **4–13 cm**
  （中位 7.2），远快于 FPS 的 20–40cm —— MC 视野 96° 水平、目标大、频繁 180°，
  不能套 FPS 舒适区。取目标 8cm（略保守，照顾串流延迟）。
- **加权求解**：各 DPI 达成 8cm 所需 s = 400→0.70 / 800→0.487 / 1200→0.383 / 1600→0.290；
  按 DPI 分布加权 = 0.52×0.487 + 0.24×0.290 + 0.17×0.70 + 0.07×0.43 = **0.472**；
  目标 7cm→0.529，9cm→0.423，故合理区间 0.42–0.53。**0.5 在区间内且是 MC 原生默认**，
  两独立理由指向同一数，不取 0.472 这个非众数非默认的奇值。
- **gain 与 slider 是立方根关系**：`s' = (g^(1/3)(0.6s+0.2)-0.2)/0.6`。达成 8cm 的
  gain 对照：400→190%、800→100%、1000→86%、1200→77%、1600→42%。
- **发现并修掉写入被覆盖的疑云**：15:14 那轮写入 0.5 后，15:16 文件被改回 0.2535211
  （字节数 2266 vs 2260，差 6 字节正好是 "0.2535211" 与 "0.5" 之差，可当指纹）。
  给 `launch-remote.ps1` 加三处快照（pre-launch / +8s / +33s，含 bytes + mtime），
  15:23 重跑三处均为 `mouseSensitivity:0.5 bytes=2260 mtime=15:23:09`，未被改写；
  15:23:35 进服。此后每次启动都会留下这条可追溯记录。
- 文档：`docs/mouse-sensitivity-default.md`（含全部数据表、公式、加权过程、DPI 对照表、
  局限）。提交 `bd88a63`。

## #78 P1 可观测性：RTT 方向修正 + 码率/交接延迟/关键帧请求（已实现/已部署）

- **RTT 协议方向本来就是反的**：前端只回答服务端发来的 `{"type":"ping"}`
  （`lib/webrtc.js:775-777` → 回纯文本 `pong,<epoch_s>`），并用 `latency_measurement`
  作 `currentRoundTripTime` 为 null 时的兜底（`selkies-wr-core.js:3687`）。
  旧实现：`classify("pong,...")` → `Action::Unknown` 丢弃；`Action::Pong` 反而给客户端
  回一个没人要的 pong。→ 从未测过 RTT，`rtt_ms` 从来是空。
- 新 `signaling/latency.rs`：`LatencyProbe`，1s 一个 ping，**用本地 `Instant` 计时**
  （payload 是浏览器时钟，相减得到时钟偏差），EMA α=0.3，5s 无回执计 lost，
  通道没开时 `cancel_pending()`（否则「没发出去」被记成「丢了」）。首条回复打一行 info。
- **验证**：日志 `rtt probe: first ping sent on the control channel` +
  `rtt probe: first reply 6.9 ms`（局域网被控机，DC 走 SCTP）。
- **码率/延迟**：`pipeline_ms` 停在编码器出口，队列等待不可见。队列元素改
  `Sample{data, beat}`，forwarder 在 `write_sample` 返回后计时 → `send_ms`（与
  pipeline_ms 之差 = 链路积压）。`bytes_sent` 只计**成功入队**负载；`peak_mbps` 取最宽
  250ms（<50ms 的桶丢弃，否则单个 60KB 关键帧读成 60Mbit）；`target_mbps` 直读
  `encoder.bitrate()`。PLI/FIR → `pli_requests` → 面板 `keyframe_requests`。

  `send_ms`+`send_min_ms`/`send_max_ms`/`rtt_ms`/`keyframe_requests`，改名 = 永久显示「–」。
