## 09:00 视频设置五控件（#92）：一条真 bug + 一条真缺能力 + 三条「没这事」

用户报「编码器 / 码控 / 视频码率 / 覆盖层 CRF / 覆盖层连发」都改不了。

**根因三条**

1. **`min === max` 与 `undefined === undefined`**（第三次踩）：面板控件判禁用是
   `serverSettings.video_bitrate?.min === serverSettings.video_bitrate?.max`，
   键不存在时两边都是 undefined → 灰。`audio_bitrate`(#91)、`scaling_dpi`(#90) 同款。
   → 服务端宣告 `video_bitrate {min:200,max:40000,default:8000}`；`vb,<kbps>`
   本来就通到 `set_bitrate_override`，链路一直是好的，只是点不到。
2. **码控只有 CBR**：`allowed:["cbr"]` → 下拉框灰。这次真做了 CQ 模式。
3. **覆盖层三项**：判灰原因同 1，但**本管线没有 paint-over（区域重绘）**，
   可调就是假旋钮 → 宣告 `locked:true`，面板整行隐藏。

**CQ 实现要点**（详见 `docs/video-knobs.md`）

- libvpx 的 `rc_end_usage` 不能在活编码器上改（`vpx_codec_enc_config_set` 校验
  与初始化不一致就拒），所以模式必须在 open 时定：`VpxEncoderConfig.rc / cq_level`
- 换模式走 `InnerOutcome::Rebuild`（和改分辨率同一条路）
- CQ 下 bitrate 只搬上限（新 `set_target_bitrate`），**不能**用 `set_quality(ratio)`
  —— 它会按 ratio 重算量化器，把 CRF 悄悄抹掉
- 默认仍是 CBR；`_rc,`/`_crf,` 从 B 组噪音改成真指令（前端早就发这俩，缺的是服务端）

**编码器那一行**：`fixedEncoder` 时改事实行 `VP8 · 服务端唯一`（`.setting-fact`），
灰掉的下拉框在这类场景永远像「坏了」。真要 VP9 得动 RTP 轨道与打包器。

**测试环境坑**

- `vswhere` 在这台机器返回空 → `$vsRoot` 空 → 报 `C:\VC\Tools\MSVC` 不存在；
  直接写死 `C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools`
- 用 `cmd /c vcvars64.bat` 套环境会被工具的安全策略挡下，只能按 deploy.ps1 的
  方式手工拼 PATH/INCLUDE/LIB，再补 `LIBOPUS_LIB_DIR`

**验证**：107 单测（+4：CQ 在 crf 5/25/50 真能 open、默认与 clamp、wire 名、
`_rc` 不再是噪音）；线上 pid=8508，日志 `VP8 encoder opened: … rc=cbr crf=25`、
`new encoder: … rc: Cbr, cq_level: 25`。后端 `8dde521`、前端 `53aaeda`，已推送。

**注意**：cloud-stream 仓库的 `main` 没有 upstream，`git push` 会静默失败 ——
要写 `git push origin main`。上一次（10-29 的 `8c33bd6`）就是这么漏推的。

## 10:30 虚拟机状态 API（#93）：`/api/v1/health` + 两个控制 POST

需求四问已与用户对齐：判活=**进程 + 推流健康**；数据面=主机资源/推流状态/
进程与游戏/连接数与 IP 与设备码；**不做鉴权**；只读 + 少量控制。

**判活的核心不是端口，是 `last_sample_at`**

`/api/status` 只知道"进程还活着"。这次的判据是 `PipelineStats.last_sample_at`
—— 上一次有帧真正写进 track 的时刻，**新帧和重复帧都算**（静止桌面本来就只发
重复帧，只有"什么都没出去"才是卡死）。3 秒沉默 → `verdict:"stalled"` + **503**；
状态码就是结论，监控只看 200/503。

**五种结论**：`idle`（没人连）/ `starting`（首帧未出，<15s）/ `streaming` /
`paused`（客户端 `STOP_VIDEO`，是用户操作不是故障）/ `stalled`。只有 stalled 不健康。

**踩到的坑：`FrameCounters` 不是窗口值**

实测 `repeat: 534` 配 `new: 1` —— 它由统计定时器每秒清零，而定时器**只在面板
统计开关打开时才跑**。面板关着时就是自采集循环启动以来的累计值。所以原本写的
`capture_error_this_window` 三个 flag 会说谎，改成探针自己记基线做差
（`errors_since_last_check` + `checked_ago_ms`，首查为 `null`），字段名也从
`frames` 改成 `frames_total` 防误读成速率。

**其他要点**

- `SessionRegistry.info` 用 **std Mutex**（值小、不跨 await、发布在 select 分支里，
  读在同步 HTTP handler 里）。用 tokio Mutex 会让 `publish/clear_if` 编译不过。
- 采样 5 秒缓存：全进程扫描在 Windows 上几十毫秒，监控每秒 curl 会把被观测机拖慢。
  进程表用 `ProcessRefreshKind::new().with_cpu()`，**故意不刷 user**（每进程查 SID
  是一串 LSA 调用）。
- `game_running` 只是名字启发式（javaw/java/minecraft*.exe），`top` 才是原始事实。
- 设备码：前端新增 `util.js:deviceId()`，**localStorage**（原有 `pageTabId()` 是
  sessionStorage，关标签即失效），随 hello 的 `client_device_id` 上报。
- 安全骨架：`Endpoint::Health` 归 `is_observational`，`Endpoint::Control` **不归** ——
  将来"能探活/能看连接/能踢人"可以分别授权。
- 编译坑：`ClientMeta` 要在 `head` 被 move 进 `PrefixedStream` **之前**构造，
  否则 `headers` 还借着 `head` → E0505。

**验证**：117 单测（+10）；两次部署；实测 200/streaming、二次轮询
`checked_ago_ms:2305`、`capture/restart` 202 + 日志
`control: capture/encoder rebuild requested over HTTP`、拼错动作 404 带白名单、
GET 控制端点 405、`session/kick` 200 后客户端 2 秒内自动重连（id 2→4）。
`device_id` 目前仍是空串：浏览器还跑旧 bundle，硬刷一次才有。
