## WebSocket + WebCodecs 收尾：四项缺口一次做完

上一轮分析列了四条，全部落地并部署（pid 4908，exe md5 `6C806BAD…`）。
分四笔提交：`c9c20dc`（transport）、`ff2baa0`（stats 租约）、`8e6827c`（WS 三件事）、
`88768f5`（docs），前端另一仓 `6d33406`。

**传输选择的三层优先级，错一层就出"开关没用"**：`?transport=`（一次性，用完
`dropTransportParam` 从地址栏摘掉）> `/api/status.current_mode`（**只在这个浏览器
没存过选择时**播种 localStorage）> localStorage。绝不能再用
`window.__SELKIES_STREAMING_MODE__` 注入 —— core 的 `determineStreamingMode` 把注入
排在存储之前，往 window 上发布会把面板的每次切换在下次加载按回去。

**`/api/status` 从纯文本 `ok` 改 JSON**：`{"status","current_mode","enable_dual_mode",
"transports"}`。看门狗/部署脚本只看状态码，不受影响。`server_settings` 同时补
`enable_dual_mode: {value:true, locked:false}` —— `Sidebar.jsx:2804` 靠它决定渲染不渲染
那个切换项，之前不发是因为没有第二条传输可切。

**`AUTH_SUCCESS,{…}` 那个前缀比想象中重要**：页面是 `startsWith('AUTH_SUCCESS,')` 后
`substring(13)` 再 parse（`selkies-ws-core.js:8407`）。裸 JSON 会落进 `startsWith('{')`
分支，`obj.type` undefined，整条静默丢弃，`clientRole` 永远 null —— viewer 拒不掉，
控制权也不落定。

**扁平封套 vs 嵌套封套**：WS 页面读 `obj.info` / `obj.stats`，不是 `{type,data}`。
这是 `settings_frame` 已经踩过的同一个坑。设置表仍用 `full.get("data")` 拆包复用
`dispatch/output.rs`，不复制第二份 150 行 —— 单一事实来源留在那边。

**JPEG 条纹（`0x03`）是"任何浏览器都能看"的唯一保证**。`pipeline::raw` 全局 tap：
`publish()` 先原子读订阅数，0 就返回；有人订才 `Bytes::copy_from_slice` 拷一份 BGRA；
队列 2 帧、满了丢新帧不阻塞采集线程；`RawSubscription::drop` 自动退订。
线上格式头 6 字节 `[0x03, _, id_hi, id_lo, y_hi, y_lo]`，同帧多条共用一个 id，
`y` 是条带顶端行号，页面画到后缓冲，最后一条到画面底边才呈现。
**只在页面把 encoder 切成 `jpeg` 时才走** —— 前端 `canProcessJpeg` 只认
`currentEncoderMode === 'jpeg'`，而它唯一来源是 `server_settings.encoder`，
所以切 JPEG 必须回 `encoder: {value:"jpeg", allowed:["jpeg"]}`。

**静态桌面是这条路真正的坑**：DXGI 静止时不出帧，`raw::publish` 原来只在新帧路径调用，
探针连上去 4 条（一帧）之后就超时。光标重绘和 `WouldBlock` 重复帧两个分支也得发，
JPEG 观众在黑屏上等的正是这两条。修完：`RESULT ok stripes=8 frames=2 bands=4
y=0/270/540/810`（1080÷4=270）。副产物是发现静态桌面约 4 秒才重复一帧，
所以重复编码 JPEG 的开销可以忽略，不必做"内容未变就跳过"的优化。

**统计窗口不能是单向开关**：`claim_stats` 原来是 `AtomicBool::swap(true)`，第一个订阅者
永久拥有，它一关就没人再 `publish_snapshot`，后来的会话读到定格快照，`encoded_fps`
永远不变 —— 稳定得像正常，错得最难发现。改成 `Mutex<Option<Instant>>` + 3 秒租约，
发布即续租；tick 是 1 秒，连丢 3 拍才判死。

## WS 麦克风上行（#110）：打通 + 两个实测缺陷

- 前端事实（`selkies-core` mic worker）：WS 上行帧 = `[0x02] + Opus`，编码参数写死
  **24 kHz 单声道 / 20 ms / 480 采样**（WASM 回落同一组）。页面收到
  `MICROPHONE_DISABLED` 会 `microphoneEnabled=!1` 并停采集，所以拒绝语义不变。
- 实现：`audio.rs` 把原 `run_uplink` 拆成 `pump(stop, rx, idle)`，WebRTC（idle=None，
  设备常开）与 WS（idle=Some(1.5s)，首包才开、空闲关）共用解码+写设备；
  `MicUplink::start()/push()` 是 WS 注入点，队列 8 包、超长/空包本地丢弃并计数。
  `ws_media.rs` 的 `0x02` 分支接上，同一套 `input_policy` 门禁（拒绝计 `denied_inputs`）。
  health `stream.audio.uplink.live{open,packets,frames,dropped,decode_errors,concealed,
  silence,last_packet_age_ms}`。
- **关键假设已由测试固定**：24k 单声道包用 48k 立体声解码器解 → 960 采样/声道、
  单声道复制到双声道（`a_24k_mono_packet_decodes_into_one_48k_stereo_frame`）。
  不需要服务端重采样器。
- **实测缺陷 1**：注入端旧实现"把 free 全填满"，缓冲里恒为 `数据20ms+静音80ms`，
  4.8s 语音被补 58560 采样/声道（≈1.2s）静音 → 断续"哒哒"声。
- **实测缺陷 2**：只把目标降到 50ms 还不够 —— 每 5ms 转一圈、包每 20ms 来一个，
  若仍"补到位"，静音始终领在数据前，静音反涨到 123840。正确做法：播放中只写手上
  真有的帧，没数据就什么都不写；静音只用于未开播时的端点保活。复测：240 数据帧、
  静音恒 4 帧（80ms，仅开播前），不随时长增长。
- 顺带量到：`Initialize` 请求 100ms，`GetBufferSize()` 实测 4800 帧 = 100ms（真的）。
- 验证（.148，VMware，`--mic-device default` 因为没装线缆）：自建 WS 客户端用 ffmpeg
  产 24k 单声道 Opus（RTP 抓包后剥 12 字节头）发 240 帧 → `packets=frames=240`、
  `decode_errors=0`、`dropped=0`、`open=true`，日志 `microphone uplink open (110 B 首帧)`
  + `uplink playing (140 ms buffered)` + `render open ... buffer=100 ms (4800 frames)`。
  空闲 1.5s 后 `open:false` + `render closed`。
- 部署：md5 `DD3FFE030E1DA853280350833A7E3CC0`，pid 7204。
  **`toolchain/start-stream.cmd` 临时加了 `--mic-device default`**（对讲模式，会自听），
  目的是在这台没线缆的机器上验链路；装了 Steam/VB-CABLE 的机器应改回 `auto`。
- 测试 266 passed。

## #110 租户隔离六项改造（同日晚）

前置分析结论：仓库里原本没有任何 `tenant`/`org`/`account` 概念，只有**会话隔离**，
且默认 `--input-policy shared` → `viewer_may_run` 白名单**从不执行**，观众与主控者
没有区别。

六项逐个落地：

1. **codec/audio 从进程级下沉到 `SharedPipeline`**：删 `codec::CURRENT`、
   `audio::TARGET_BPS`/`ENABLED` 三处 `static`；`StreamSettings` 新增
   `codec/audio_bps/audio_enabled` 三个 `Arc<Atomic*>`（`clone()` 即共享，天然挂
   program）。`audio::spawn(fanout, stop, bps, enabled)`。codec 变更改为
   `kick_display`（只踢同一块屏），SDP 回退只改本会话不再踢所有人。
2. **默认 `InputPolicy::Exclusive`**，SETTINGS/切屏/输入统一过
   `ControlGate::owns()`；WS 侧新增 `touches_program_settings(payload)` 做**字段级**
   裁决（整条拒 `SETTINGS` 会连带丢掉 tabId 与选屏）。
3. **`ws_media` 接入 `security::allow`**：此前这条路径一条裁决都没有，装真策略也
   是空心的。顺序 = 角色（`owns_input` + `viewer_may_run`）→ 策略。
4. **凭据带身份**：`Grant{tenant, role}`、`GrantSpec` 解析 `--auth-grant
   <tenant>:<role>:<token>`（`splitn(3,':')`，令牌放最后因可能含冒号）、
   `Principal.tenant/role`、`TokenGate` 改多条目。`websession::run` 现在收 `grant`
   并把真身份带进 DataChannel 闭包（原来硬写 `Principal::default()`）。
5. **`/api/v1/health` 按租户过滤** + `viewer{tenant,role,credential,hidden_clients}`；
   `encode_node` 走 `StreamInfo::expose_node`，降权时**删键**而不是发空串。
6. **上传目录按租户分根** `<upload-dir>/<tenant>/`（默认租户也走子目录，不留
   直接用根的例外，否则一次列表就把别人的目录名全列出来）+ `--upload-quota-mb`
   （默认 512，0=不限）超额回 507。

**踩到的两个真洞（都已修 + 测试固定）**：
- `Principal::with_grant` 曾把 "viewer + 原本没凭据" 记成 `Credential::None`，而
  `None` 的含义是"这部署没有门" → **任一 viewer 令牌因此拿到操作权**。
- 反过来：`role == Viewer` 且真的没配令牌时，`may_operate()` 为假，会把**单用户
  部署自己的键鼠挡掉**，且日志全绿。修法是判据上移到 `Principal::may_operate()`
  = `role.may_operate() || credential == None`。

`--policy auto`（新默认）：无令牌表 → `allow-all`，有令牌表 → `role-based`。
`role-based` 是唯一真读身份的内置策略。

## P1：默认录音设备切换（收掉 #109 的最后一块）

- **做了什么**：`platform/default_mic.rs` 用**未文档化的 `IPolicyConfig::SetDefaultEndpoint`**
  把 console / multimedia / communications 三个 role 一起切到虚拟麦的 capture 端点。
  `--mic-default-device auto|off`，默认 auto。health 的
  `stream.audio.uplink.default_device` 报 `action/policy/device/current/previous/restored`。
- **时机改了一个字**：文档原写"会话开始时切"，实际必须**启动时切** —— 游戏在启动时
  读一次默认设备就缓存了，会话开始才切等于没切。代价是被控机本地录音软件在服务运行
  期间拿到虚拟麦，所以必须能还原。
- **`windows` 0.52 没有 IPolicyConfig**（元数据里没有）。手写 vtable：照抄该 crate 自己
  生成的接口写法（`#[repr(transparent)] struct X(IUnknown)` + `unsafe impl Interface` +
  `ComInterface`）。方法顺序是硬约束，`SetDefaultEndpoint` 在 IUnknown 三个槽之后第 12 位，
  前 11 个只占位。CLSID `{870af99c-...}` / IID `{f8679f50-...}`。
- **最大的坑不是 COM，是停止方式**：部署/看门狗/关机都用 `Stop-Process -Force`，
  进程拿不到 Ctrl+C，`restore()` 永远不执行 → 只靠"退出还原"等于一次部署就把默认录音
  永远留在虚拟麦上（本地麦克风全静音，看起来像驱动坏了）。补了原值落盘
  `logs/mic-default.json`：切换前写、正常退出删、**下次启动读到它就说明上次没还原，
  接管还原责任**（文件里的才是真正的原始设备）。`--mic-default-device off` 兼作撤销。
- **验证（.148，四步闭环）**：switched（previous=麦克风）→ `taskkill /F` 后 already +
  "发现上次未还原的记录" → `off` 得 restored（3 个角色）+ 文件被删 → 再启动 previous
  又是麦克风（反证还原生效）。pid 7708，exe md5 `12D37DD644B36E2EE03127EAE936DDD7`，
  295 单测全绿。
- **新工具** `toolchain/mic-default.ps1`（`-List` / `-Name` / `-Id`）：C# 里独立声明同一套
  IPolicyConfig，不依赖服务就能读写默认录音。两套独立实现都成功 = 互相校验了 vtable 顺序。
- **环境教训（第三次踩）**：Bash 里编译必被 Git 的 `link.exe` 抢走；带 `del /q` 的
  ssh 命令会被沙箱拦；ssh 里嵌套引号的远端 shell 调用会被吃三层，落地成 .ps1/.cmd +
  scp 才是确定性的做法。`start /b` 起的进程参数会被吞（`--log logs\x.log` 丢了），
  批处理文件传参才可靠。

## 修：WS 下切 VP9 后无限重连（页面卡在 "WebSocket disconnected"）

- **根因（不是编码器坏了）**：换编码器必须断连接重协商，而单观众时那条连接就是
  最后一个持有者 → `PipelineRegistry::release` 摘掉程序 → 新连接 `acquire` 用
  `StreamSettings::from_config(cfg)` 重建 = CLI 默认 VP8 → 页面读到 vp8 再把偏好
  推一次 → 再断。日志指纹：`last session left … codec Vp9` 紧跟
  `attached as session N (… codec Vp8)`，无限交替。
- **错误前提**：`settings.rs` 原注释断言「程序 outlive 它上面的每个会话，所以 pick
  跟着重连存活」。#110 把 codec 从进程级挪进程序时这句话只对「还有别的会话挂着」
  成立，单页签最常见的路径上失效。
- **修法**：`StreamPrefs`（值快照）+ `PipelineRegistry.prefs`（按 `DisplayKey`
  记）。`release` 摘程序时存、`acquire` 建程序时套。fps/分辨率/码控/CRF/音频
  一起继承（同一次重连会一起丢）。
- **坑**：`StreamSettings::clone()` 是**浅**拷贝（全字段 `Arc<Atomic*>`），拿来当
  快照等于存别名 —— 专门写了 `prefs_are_a_snapshot_not_an_alias` 盯它。
- **部署**：299 单测全绿，pid 1924，exe md5 `2D67A936C302ABDB1614D77FDD28A85F`。
- **验证手法（下次直接抄）**：exclusive 策略下页签持租约，探针是 viewer，
  `encoder` 在 `touches_program_settings` 里 → 改设置会被**静默拒绝并回真实值**，
  看起来像"改了没生效"。借租约 `POST /api/v1/control/session/take/<id>` 后重推
  vp9：3 s 内 182 帧、帧头 `[1] >> 4 == 3`、连接不断 → 闭环，测完把租约还给原
  session。另注：`AUTH_SUCCESS` 里**没有 session id**，探针要靠 health `clients`
  的差集认领自己那条连接（`mic-push.py` 早就这么干）。
- **顺手订正**：`docs/codec-choice.md` §5 那张"VP9 约 2x"的表方向反了（实测
  VP8 21–23 ms/帧、VP9 7–8 ms/帧），已改成实测值并写明原因（VP8 real-time 不做
  token partition 并行；VP9 开了 row-mt + tile-columns + VP9E_CONTENT_SCREEN）。
  新增 §7 记录这次死循环。

## WS 控制面自激（SETTINGS ↔ server_settings 回执环）

- 现象：页面长期 "Waiting for stream"、反复重连（服务端已登记到 session 44，最近
  每 25–40 s 断一次）；**WS 数据面其实是通的**（60 fps / 5.6 Mbps / write_err 0）。
- 取证：`stream-server.log` 涨到 337 MB（+167 KB/s ≈ 4 GB/h），内容 99% 是
  `SETTINGS: framerate/audio bitrate/rate control/crf/manual resolution`，
  折算 **约 400–550 批/秒**；每次回执 1392 B ⇒ 下行约 4.7 Mbps 是 JSON，占一半带宽；
  进程 CPU 86%。健康接口 `stream.timing.pipeline_ms` 尚在预算内，但几乎全是这次风暴的账。
- 根因链（已用真实 `server_settings` 复现，见 `target/tmp-sanitize-loop.js`）：
  1. `ws_media.rs:1255` 每批 SETTINGS 都回一条 `server_settings`；
  2. 前端 `selkies-ws-core.js:8752-8755` 把 `sanitizeAndStoreSettings` 报出的
     `changes` 立刻 `handleSettingsMessage(changes, true)`；
  3. `:6186-6188` `settingsChanged` → `sendFullSettingsUpdateToServer(...)` 再发一整批；
  4. 而 `:1694-1700` 的 locked 分支用 `getBoolParam(key, !serverValue)` 取默认值，
     且 `:5984-5986` 在 `fromServer=true` 时把 storeBool/storeInt/storeString 全变空操作
     ⇒ `use_cpu / video_fullcolor / video_10bit / webcam_enabled` 四个键**每轮都算"变了"**，
     永远收敛不了。
- 只在 WS 出现：WebRTC 没有"每批 SETTINGS 回执"，回路不成立。
- 待办：服务端回执改边沿触发（状态没变 + 请求值都已生效 → 不回）+ 100 ms 合并；
  前端 locked 分支默认值改 `serverValue`、服务端回执不触发回写。另：`STOP_VIDEO`
  已在 `:650` 真的停发，但重连churn 说明第一帧始终没出画，先修风暴再复测。

## WS 没有指针（#111）：事件通道从没订过

- 现象：WS 模式下画面在流（60 fps），但指针不在——页面 `updateServerCursor`
  从未被调用，因为它只认 `cursor,{json}`，而 WS 的 `run()` 里**一条
  `add_event_sink` 都没有**。WebRTC 一直有（`websession.rs` 的转发循环），
  所以这是"只有 WS"的独有缺口。
- 修法：`ws_media.rs` 按**程序**订阅 `PipelineEvent`（不是按连接），只消费
  `Cursor` → `cursor,{data}`；换屏时 `remove_event_sink` + 重新挂；连接/换屏
  各补发一次 `handle.last_cursor()`。`PipelineHandle` 新增 `last_cursor` 缓存
  （`emit_event` 里顺手写，`None` = 还没读到过，`Some(id 0)` = 现在隐藏）。
- 补发的顺序坑：`last_cursor()` 要等采集第一次 beat（在 `handle.start()` 之后），
  而补发跑在它前面 → 多半拿到 `None`；指针形状又不会自己变（`update_cursor`
  只在 id 变化时 emit），于是"等下一次变化"可能永远等不到。加 250 ms 补位定时器，
  拿到一条就永久关掉那一支。
- 顺手修：`cursor_png_b64` 把 BGRA 直接写进声明为 **RGBA** 的 PNG（红蓝对调）。
  白箭头看不出来，彩色指针会错；抽成 `cursor_rgba_rows` 并加回归测试。
- 一次性诊断：采集第一 beat 打一行 `#111 host cursor: id … / hidden / single-colour
  / GetCursorInfo failed` —— 这四种下游长得一样（都是 `None`），只有这行能分开。
- 验证：本地 8099 明文服 + `toolchain/cursor-probe.py`（`WSPLAIN=1`）→ 1 条
  `cursor,`、32x32、387 B b64、VERDICT=PASS。
- **.148 上仍然 0 条**，一次性日志给出真因：`host cursor: id 0x10005 is
  single-colour` —— 虚拟机控制台的指针是 `CreateCursor()` 造的单色光标
  （hbmColor==0，只有 AND/XOR 两张 1bpp 掩码），旧 `cursor_data` 直接跳过。
  补上 `monochrome_cursor` + `compose_mono_mask`（透明/黑/白/反色四格），
  `read_dib_topdown` 抽成 helper（颜色平面 BI_BITFIELDS，掩码 BI_RGB）。
  用 `CreateCursor` 在单测里造真单色光标端到端验（左右半不对称，能查出
  AND/XOR 读反）。复测 PASS：32x32 hot=(8,9)，解出 PNG 是 I 形文本光标。
- 另修 `base64_encode` 不补 `=`（页面把它拼成 CSS data-URI，没有 atob 的宽容）。
