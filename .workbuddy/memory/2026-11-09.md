## #118 修 avsync 空转 + 补音频 5 s 观测

### 根因（先量后改，符合"没有这个数就只能猜"）

线上日志每行都有 `av=`，实测 `av=-140687920ms/70963fix`：媒体钟比墙钟慢 39 小时，
每 2 s 补一个 20 ms 静音帧，两天半补了 70963 次。

真因是**取数**而不是算法：`Loopback::drain()` 在有 500 ms 超时、没声音播放时直接
返回空（注释自己写着 "a machine with no playback at all legitimately never
signals"），于是 `emit_frame` 不被调用、`note_audio` 不前进；而 `fix()` 用的是
`now - started_at` —— 墙钟照走、媒体钟不动，差值就是服务运行时长。

补观测后第一次实测：连续几窗 `audio 5.0s: cap=0 ... (no frames: endpoint idle)`。
在被控机交互会话里播 15 s 声音（schtasks /IT + WPF MediaPlayer，因为 ssh 落在
session 0 没有音频设备）后变成 `cap=240 ... => 48.0 fps, 61.9 kbps`。

### 修法

`State` 里 `started_at` 换成 `wall_us`：**墙钟只在两次 `note_audio` 之间累加**，
间隔 > `MAX_FRAME_GAP`(250 ms) 判为停顿 → 重新对齐（`wall_us = audio_us`），
不把缺口算成漂移。`fix()` 在 `now - last_note_at > 250ms` 时返回 `None`；
warm-up 改成按**音频时间**算（`audio_us < 1s`）。`report()` 改成结构体，多一个
`idle_ms`，日志里 `av=+188ms/5fix idle=14398ms`。

实测：播放中 fixes 涨到 5（首批 200 ms 缓冲按 2 s 一步回压），静音后 4.4/9.4/14.4 s
三窗 fixes **一直是 5**，`idle=` 递增 —— 旧版同样时长会再多 7 次。

### 音频 5 s 摘要（§2.12 的日志那条）

`pipeline` 每 5 s 多一行：`audio 5.0s: cap=240 enc=240 bytes=38721 sil=0 =>
48.0 fps, 61.9 kbps`；`cap=0` 时行尾写 `(no frames: endpoint idle or device gone)`。
`sil` 与 `cap=0` 不是一回事：静音混音仍产包，空闲端点一个不产。

## #120 `target_kbps` 口径修正（追加）

- **根因**：`pipeline/mod.rs:1826` 在每次编码成功后写
  `s.target_kbps = encoder.bitrate()`。而 CBR 下 `set_bitrate_kbps()` 走的是
  `set_quality(ratio)`，`bitrate()` 回读的是 libvpx 按 `base × ratio` 算出的
  **配置值**，与 QoS 控制器内部的 `target_kbps` 是两个量。实测：决策 1581 /
  回读 4527，于是面板出现"throttled: true + target 4527"而实际跑 1.5 Mbps。
- **拆成两个字段**：`PipelineStats.target_kbps` = 决策（QoS 步进 / `vb,` 覆盖 /
  fps 缩放预算），`encoder_kbps` = 编码器自报。写入点只有三处，都在"做出决策"
  的地方；每帧那处改成只写 `encoder_kbps`。启动时用
  `qos.base_kbps()` + `encoder.bitrate()` 播种，避免首秒读 0。
- **health 侧**：`snapshot_fields` 从 14 元组改成 `StreamFields` 结构体 —— 第 15 个
  字段再往元组里塞就没法读了，而 §2.12 的音频三字段还要来。`health.stream` 与
  `stream_stats` 都多一个 `encoder_kbps`（新键，旧面板看不到就忽略，不会画错）。
- **测试**：326 → **331**（新增 `stats::` 两条：两值独立、窗口重置不清码率对）。
  部署 pid **5024**，实测 `target_kbps=5000 encoder_kbps=5000 throttled=false`
  （正常态两值本来就该相等，分叉只发生在改档没落下去的时候）。
- **教训**：一个字段同时承载"想做的"和"做成的"，在两者一致时完全看不出来，只在
  它们分叉的那一刻骗人——而那一刻正是唯一需要读它的时候。同类结构参考
  `default_device` 的 `current` / `previous`。
