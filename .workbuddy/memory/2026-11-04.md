## 拆会话收尾：视频门的非对称放行 + 二次部署

接 2026-11-03「拆会话（#101）」。首次部署（pid 3680）完成后自查发现一个必踩的洞：

- **症状**：`viewer_may_run()` 把 `StartVideo` 也挡了。视频门（`PipelineHandle::video_on`）长在共享程序上，门一关循环连采集都不做（`pipeline/mod.rs:1170` 的 idle beat），黑的是**所有**会话；而浏览器在页签隐藏时会发 `STOP_VIDEO`（`selkies-ws-core.js:6330`），可见性恢复时发 `START_VIDEO`，3 秒无帧重发三次后强制重连（`:4612-4630`）。
- **必然复现的路径**：同一浏览器开两个页签，切到 viewer 那个 → controller 页签隐藏 → 发 STOP_VIDEO（controller 有权）→ 门关 → 正在看的 viewer 黑屏 + 重发被拒 + 强制重连 → 自我维持的刷新循环。用户手工验收第一步就会撞上。
- **改法**：`viewer_may_run` 增加 `Action::StartVideo`，`StopVideo` 仍只归 controller。理由写进函数注释：开门幂等、只花 controller 本来就要花的编码代价；关门会毁掉别人的画面。代价是"controller 手动暂停"在有人看着时不持久——另一个方向的故障（viewer 永远恢复不了）在浏览器侧没有出路。
- 新测试 `a_viewer_may_open_the_video_gate_but_not_close_it`（START 放行 / STOP 拒绝 / 输入与设置拒绝 / 读类放行）。
- **遗留（下一步）**：扇出层没有按 sink 暂停。viewer 切后台时 STOP 被丢，服务端仍往那条 track 写帧。上游做法是 `sharedVideoPaused` 只停这一路；正确实现是给 `VideoFanout` 每个 sink 挂 `want`，写帧时跳过，并把全局门改成"有人想要就算开"。已写进 `health-api.md` 与 `roadmap-multi-display-multi-input.md §5.1`。

验证与部署：
- `cargo test -p stream-server` → **191 tests / 190 passed / 1 ignored**；release 重建 1m39s。
- 二次部署 `deploy.ps1 -SkipBuild` 79.9s：pid 3680 → **1792**，exe md5 `9BD35F60F047E6EBBDD1F684B2C9E014`，health `idle` 带 `pipelines{count:0}`，部署时 `clients.count: 0`（无人被踢）。

环境坑（本轮新增）：
- `Bash`/`PowerShell` 工具会偶发 `SandboxError(0xFFFFF826) center 规则快照不可用`，重试即恢复；后台 PowerShell 任务被沙箱拒绝读 `C:\dev\tools\pwsh\hostfxr.dll`（`0x80070005`），所以**构建与部署必须在 PowerShell 工具里前台跑**，不能用 `run_in_background`。

## P0 计量 + 准入（#102）：为“一台机器服务多个用户”先拿到真实数字

背景：方向定为「每人独立桌面/独立存储/进程隔离」后，逐条核对发现 **L2（同桌面分窗）被输入隔离判死**——Windows 输入链只有 `PostMessage(HWND)` 一个可分叉点，键盘/IME/光标/快捷键都走「系统输入队列 → 每桌面唯一前台窗口」。所以 L2 不做，多用户只能是 L3（每用户一个 session），而 L3 在 Windows 上受许可与 3.5GB/会话限制，Linux 多 seat 才是正解（~0.8GB/seat）。

在这一串结论落地之前，先做了与路线无关、且能产出决策依据的部分。

代码：
- `pipeline/fanout.rs`：新增 `SinkCounters`（bytes/frames 原子）+ `SinkHandle`；`inner` 从 `Vec<(SinkId, VideoTrack)>` 改为三元组；`attach` 返回 `SinkHandle`；`write` 在 **写成功之后**累加（按尝试计会把没出去的字节算成流量）。
- `pipeline/shared.rs`：`attach` 返回 `SinkHandle`，`detach` 仍收 `SinkId`（用 `handle.id()`）。
- `signaling/websession.rs`：`SessionInfo` 加 `sink: Option<Arc<SinkCounters>>` 与 `reconnects: u32`；`SessionRegistry` 加 `seen: HashMap<device_id, u32>`（在 `publish` 里计数，首次为 0）与 `set_sink()`；新增 `Admission` / `AdmissionPermit`（CAS 抢名额，`Drop` 归还，`max(1)` 夹 0）；`run()` 增加 `permit` 参数并绑到局部变量。
- `http/server.rs`：`serve()` 建 `Admission::new(cfg.max_sessions)`；名额在 **WebSocket 升级之前** 取，失败回 `503 + Retry-After: 5` + JSON 体（101 之后的拒绝只能靠关闭码，前端会当成抖动进重连循环）。
- `http/health.rs`：`clients.items[]` 加 `bytes_total` / `frames_total` / `avg_mbps` / `reconnects`；顶层加 `admission{max,live}`（在 handler 里注入，不污染 `build` 的纯函数性）。
- `dispatch/commands.rs`：`r` 分支先 `split(',')` 取几何段。**这是既有 bug**：`r,1714x922,primary` 用 `split_once('x')` 会拿 `"922,primary"` 去 parse，整条变 `Unknown`；WebRTC 模式前端不带 displayId 所以线上没暴露，一开 WS 每条分辨率请求都会失效。
- `config.rs`：`max_sessions`（默认 8）+ `--max-sessions`。

验证：
- `cargo test -p stream-server` → **206 tests / 203 passed / 2 failed / 1 ignored**。两个失败是 `platform/hwenc.rs`（另一条工作线的 **untracked 新文件**）`thresholds_match_the_spec` / `unknown_is_not_promoted_to_yes`：`classify(..., "")` 时 `Vendor::from_device_id("")` 返回 `Other`，而 `Other => Support::TooOld`，与测试期望的 `Yes`/`Unknown` 冲突。与本次改动无关。
- 本地冒烟（`--max-sessions 1`）：`admission{max:1,live:0}`；第一个 WS 连上 → `live:1`；第二个被 `503`（ClientWebSocket 报 "expected 101"）；`Abort` 与 close 帧两条路径都在 0.5s 内把 `live` 归 0。
- 部署 170.8s：pid 1792 → **1960**，md5 `0897EA7BBA0E5FCF31E61C520EEDB65F`；线上 `verdict: idle`、`admission{max:8,live:0}`、`clients/pipelines count 0`。

**事实更正**：被控机不是 2 核。`Win32_Processor` 返回两个对象（CPU0/CPU1），每个 2 核 2 线程 → **4 逻辑核**，health 的 `cpu_cores: 4` 是对的。之前的密度结论（“2 核只能 1 个用户”）要按 4 核重算。

## 输入租约（#103）+ 扇出并行化（#104）：两个页签的 role 与卡顿

用户贴了线上 health：`clients.count: 2` 但 **两条都是 `role: "controller"`**，且第二个页签
「无法进行任何操作，指针也无效」。

**根因一（语义 bug，非门禁 bug）**：`SessionInfo.role` 存的是 HELLO 里的
`client_type`，而**每个页面都会自称 `controller`**（前端不区分）。服务端真正的门禁是
`acquired.created`，两者从未对齐。运维看到两个 controller 会以为门禁坏了，实际门禁是对的。

**根因二（第二个页签不能动）**：这是设计行为（viewer 只读），但**没有任何证据**能区分
「输入被拒」和「输入没到」，所以看起来像故障。

改法：
- `SharedPipeline` 加 `controller: Mutex<Option<u64>>` + `controller_id()` / `set_controller(Option<u64>) -> Option<u64>`（`mem::replace`，不是 `Option::replace` —— guard deref 到 `Option<u64>`，方法版会吞掉新值）。
- `SessionCtx::is_controller()` 改为 `shared.controller_id() == Some(self.session_id)`，**不缓存**；`ControlGate{program, session, denied}` 传进两个 DC hook，每条消息 `owns()` 现问。
- `SessionInfo`：`role` → 拆成 `client_type`（页面自称）+ `display` + `denied: Arc<AtomicU64>`；`role` 由 health **现算**（同 display 的 program 的 holder 是不是这个 id），未 attach 报 `pending`。
- 拒绝时 `gate.refuse()` 累加，health 出 `denied_inputs`。
- 新增 `POST /api/v1/control/session/take/<id>`：显式移交租约（`previous` 回旧持有者）。不自动「最后交互者赢」——两个真人看同一块屏时会抢走正在打字的人的指针。
- 会话退出且自己持租约 → `registry.successor(leaving, display)` 交给同屏**最早**的幸存者；交给 None 会让剩下的人看着碰不了的桌面且重连修不好。
- 测试 +6：租约移动、按程序的动态判定、拒绝计数、successor、role 现算、pending、take 的 400/404。

**根因三（部署后暴露的严重性能问题）**：新版本上线后 `encode_ms 18247ms`、`send_ms 401ms`、
`loop 0.6Hz`、`key=33`、CPU 78%。原因不是编码器，是 **`VideoFanout::write` 串行 await**：
两个 sink 顺序写，一个慢的（未绑定/拥塞的 track）把整条管线拖住，**所有人**一起卡。
→ 改为 `join_all` 并行 + 每 sink `write_budget(spf)`（`4×spf`，夹在 50–150ms）超时丢帧。
实测恢复：`send_ms 401.5 → 4.8`、`encode_ms 18247 → 10.3`、`write_err 38 → 0`、CPU 78% → 30.8%。

部署：`731A239CD4862D52223E78B474DF6B40`，pid 1364。线上两个页签现为
`id2=controller(denied 3)` / `id3=viewer`，两者 `client_type` 都是 controller（正常）。
take/3 → `{"previous":2,"controller":3}`，take/2 → `{"previous":3,"controller":2}`，均 200。

另：10:07 那版（无转发修复）在部署后两次 `exited with -1073741819`（0xC0000005）被看门狗
拉回；新版 4 分钟无崩溃。崩溃原因未定位，怀疑 FFI（vpx/DXGI），暂记为观察项。

测试：`cargo test -p stream-server` → **213 passed / 1 ignored**。

## 输入策略 shared（#105）：两个页签都是 viewer = 谁也不能操作

用户回帖：仍然卡 + **任何键盘鼠标都无效**，上传文件正常；health 里两个会话
`role: "viewer"`、`denied_inputs` 293 / 749。日志给了完整因果链：

```
session 2 建程序 → lease Some(2)
session 2 left, 0 downlinks remain  → lease Some(2) -> None
session released (1 holders left, 0 sinks)   ← 程序没死，租约空了
session 6/7 进来 created=false → 旧代码只有 created 才写 controller → 永久 viewer
```

- **根因**：租约只由「创建程序的那个会话」写。程序比创建者活得久（刷新/断线，另一个
  页签还挂着）就永久无主，重连也修不好——租约按程序记，不按 socket 记。
- **修一**：`SharedPipeline::try_claim_controller(id)`，join 分支挂上后认领无主租约
  （CAS 语义在一个 Mutex 内，两个同时 attach 不会双赢）。
- **修二（默认行为改变）**：`--input-policy shared|exclusive`，**默认 shared**：所有
  已 attach 的会话都能注入。理由写进 config 注释——上游 Selkies 本来就没有独占输入；
  真实用法是一人两个页签；Windows 的输入隔离粒度是**会话**，独占租约换不来隔离，只
  换来「两个人都是 viewer，谁按都没反应」。
- `ControlGate::owns()`：shared 恒真，exclusive 读租约（不缓存）。`is_controller()`
  保持租约语义不动（unpin / 退出移交仍按持有者判）。
- health：`server.input_policy`；`role` 在 shared 下对已 attach 会话报 `controller`
  （这次是真的，`client_type` 仍是对照）。`denied_inputs` 只有 exclusive 才会涨。
- 测试 +3：无主租约只被认领一次、shared 下无租约也能 `owns()`、shared 下两个 role
  都是 controller 且 `input_policy` 可区分。

**「卡顿」的判断依据**（重要，别被症状带跑）：日志里每个 5s 窗口都是
`new=0 repeat=300`，`frames_total.new` 25 分钟只有 34 —— 被控端桌面**完全静止**，
因为输入进不去，画面当然"卡"在一个冻结帧上。管线本身健康：`loop=60Hz`、`enc_avg=3.5ms`、
`ws_err=0`、`write_err=0`。所以这一轮**不碰编码/传输**，先修输入；若输入恢复后仍有
卡顿，再看前端统计面板的 decode fps 与丢帧，别改 `--repeat-every` 或码率。

部署：`3DA9F20E4273385D623EDA8393A6AF64`，pid **10760**，149.6s；两个页签自动重连为
id2 / id3，都是 `role: controller`、`denied_inputs: 0`、`input_policy: shared`。

**环境坑**：`cargo test` 在 Git Bash 里直接跑会用 PortableGit 的 GNU `link`（报
"missing operand after '\377\376'"）。必须把 MSVC 的 `bin\Hostx64\x64` 放到 PATH 最前，
且 `INCLUDE`/`LIB` 必须用 **Windows 反斜杠路径**（用 `/c/...` 会 LNK1181 找不到
kernel32.lib）。




## WebSocket 传输（#106）：只读视频通路打通

**为什么做这条**：WebRTC 必须有 UDP 或 TURN；穿反代/云安全组/别人公司网络时只有 443。
前端通路是现成的（`selkies-webclient/addons/selkies-web-core/selkies-ws-core.js`，
10672 行，WebCodecs 解码 + 分行 + 音频 + 剪贴板都在），缺的一直是服务端。

**线上格式（前端是唯一规范，别凭印象）**：一帧 = 12 字节头 + 裸码流。
`[0]`=0x01 整帧（0x03/0x04 是 JPEG/H.264 分行）、`[1]`=`codec<<4|key`
（h264=1/vp8=2/vp9=3/av1=4/h265=5，`lib/wire-codecs.js:23`）、`[2..4]`=frameId、
`[4..6]`=y(0)、`[6..8]`=w、`[8..10]`=h、`[10..12]`=reference=上一帧 id。
`reference` 决定前端 `decode-gate.js:99` 是否做丢帧跟踪；填 `frameId` 等于关掉保护。

**关键帧位自己算**：`Sample{data,beat}` 不带 `key`。VP8 首字节 bit0==0；VP9 首字节
bit2==0（紧挨 profile 位，取错 = 永远黑屏）。

**握手的三个坑**：① `server_settings` 在 WS 上是**扁平** `obj.settings`，WebRTC 是
`data.settings`，发错层不报错、所有下拉框停在本地默认；② 有口令时必须先发
`AUTH_SUCCESS,{role,slot}`；③ 顺序 AUTH → `MODE websockets` → settings。

**做法**：`VideoFanout::attach_stream(mpsc::Sender<Bytes>)` 是第二种下行，
`try_send` 不 await、队列 4 帧、满则丢最新帧；`len/is_empty` 两类一起算。于是
「一个页签 WebRTC + 一个 socket」共享同一次采集与编码（实测日志：sink 1 + stream sink 2
同一 program）。`POST /api/switch` 只答应一声（前端模式菜单入口，缺它 = 404 = 点了没反应）。

**修掉广告没货**：`server_settings` 里 `webcam_encoder: vp9, locked` 改成
`webcam_enabled: false, locked`（前端 `lockedOff` 的写法），因为摄像头上行一行没实现。

**验证**：`toolchain/ws-probe.py`（stdlib 手写 WS 客户端，不装库——要验的就是线上格式）。
.148 实测 `RESULT ok frames=8 keyframes=1`，头字段逐项正确、frameId 连续、ref 链正确。
`cargo test -p stream-server` 227 passed。提交 `d911323`（7 文件）。

**没做**：键鼠注入、音频（Opus 2 字节头）、剪贴板上行、摄像头上行。所以 WS 模式
「能看不能操作」。

**踩到的坑**：① 探针只存前 120 字符做断言 → `server_settings` 被截断，假阴性
`RESULT fail`；断言看全文、打印才截断。② `settings.output()` 第一帧前是 `(0,0)`，
直接填头 → 前端 `configure({codedWidth:0})` 抛异常 = 连上但解不出；零值回落到
`width()/height()`。③ `serde_json` 的 Map 按字典序，`type` 会排在 `settings` 后面。
④ `ws_media::run` 没有 spawn 就不要 `S: Send`，否则 `handle_inner` 泛型对不上。

**协作风险（必须记住）**：并行线也在同一棵树上跑，且已在 .148 上部署自己的构建
（pid 10760、`--input-policy shared`）。我用 `swap-exe.cmd` 两次换 exe 会顶掉他们

## WS 补齐输入/音频/剪贴板（提交 9f5ba51）+ 多会话落地（提交 22695fc）

**致命 bug**：WS 视频整帧的类型字节必须是 `0x04`，此前发的是 `0x01`。前端在 socket
worker 里**先按类型分流**，`0x01` 直接进 Opus 解码器 → 码流被当音频解，视频这条路
一次都没走到过。上一轮探针也断言 `0x01`，于是"验证通过"——实现和测试一起错。
现在探针先判 `0x01` 当音频计数，视频必须 `0x04`。

**补上的能力**（都复用既有分类器，不另写解析器）：`classify` → `WinInputSink`（按
`--input-policy` 放行并计 denied）、`cr` → `clipboard_reply,cr` + WS 家族剪贴板下行
（`clipboard,` / `clipboard_binary,` / `clipboard_start,` … 与 WebRTC 的 `cb,` **不是
一族**）、音频 `[0x01, flags] + opus`。会话注册进 `SessionRegistry`（`register_media`），
退出时 `detach` 视频+音频 sink 并按 key `release`。

**音频改结构**：一条 loopback → `AudioFanout` 的 N 个 Opus sink，与视频 fan-out 同构，
观众数不再线性放大 CPU。日志确认只开了一次 loopback。

**远端实测**：`.148` `RESULT ok frames=8 keyframes=1 audio=0 text=4`，收到
`clipboard_reply,cr`。`audio=0` 是这台 VM 不播放声音、loopback 无事件，需有声机器复验。

## 多显示器（#109）：采集索引 + 输入坐标偏移 + hello 的 display_id

**切口**：`StreamSettings.display`（程序身份，不是可变参数）、`CaptureSource::open_at`
+ `geometry_at`、`WinInputSink::TargetSpace`、`--display`。

**两个不能想当然的地方**：
1. `Display::all()` 是 DXGI 枚举顺序，**index 0 不一定是主屏**，而所有老客户端都在要 0。
   所以 `ordered_displays()` 先把 primary 排到 0；请求不存在的 index 如实报错，不回落主屏。
2. 非主屏光加 origin 不够：`SendInput` 的绝对坐标必须带 `MOUSEEVENTF_VIRTUALDESK` 并对
   **整个虚拟桌面**归一化，否则 Windows 按主屏解释，指针跑到主屏去。主屏走原路径（不带
   flag），保证单屏机器零回归。

**编号**：页面 `display_id` 从 1 数（`display2` = 第二块），索引从 0 数 →
`DisplayKey::from_hello` 做 `N-1`，认不出的值回落主屏（拒绝 hello 会让人停在黑页）。

**顺带修的真 bug**：`ws_media` 的 `acquire` 改用 `cfg.display` 后，`release` 还写死成
`PRIMARY` → `--display 1` 下程序永不回收、PRIMARY 计数被扣成负数。改成释放
`pipeline.display`。

**踩到的坑**：本轮用脚本改的 5 个文件被写成 CRLF，而仓库里是 LF，`git diff` 变成整文件
重写（win_input.rs 2090 行）。`sed -i 's/\r$//'` 归一化后 diff 回到 336 行。

**验证**：`cargo test -p stream-server` 234 passed / 1 ignored（新增 4 个 from_hello/stream_info
测试）；部署 pid 8464（md5 77CCC5FB）；日志 `displays: 0:1920x1080@0,0 \\.\DISPLAY1`；
WS 探针 `frames=5 keyframes=1`；health `pipelines{count:1,display:0}` + WebRTC 会话
`display:0 role:controller`（重连后正常，说明单屏路径没回归）。

**没做**：真·双屏验收（这台 VM 只有一块屏）；WS 侧选屏（WS 没有 hello，跟 `--display`
走）；麦克风/摄像头上行仍是"广告了没货"；WS 会话的 `tabId` 未接 `update_meta`。

## WS 选屏 + 麦克风回绝 + 多屏坐标单测（提交 3cbe9c3）

**WS 选屏的真正缺口不是"没有 hello"，是没人读 `SETTINGS.displayId`。** 页面用
`#display2` 选屏，但 hash 不发到服务端；它把选择写进 `SETTINGS` 批（
`selkies-ws-core.js:3811`），服务端一直无视。现在：先按 `--display` 开一路，SETTINGS
到了不一致就 detach → release → acquire，再回 `PIPELINE_RESETTING <页面的名字>`。
两个坑：① 顺序不能反（DuplicateOutput 独占，新的一路先开会让某些卡退 GDI）；
② 必须发页面的名字（`display2`）而不是索引，它拿名字和自己的 `displayId` 比。

**`tabId` 在同一批里**，到了就 `update_meta` —— 此前 WS 会话在 health 里 `tab_id`
永远是空串。

**麦克风/摄像头**：两条上行都没有接收端，此前"收下再丢"，页面不知道。现在
`server_settings` 里两个键都 `{value:false, locked:true}`（挡自动启动），WS 侧收到
`0x02`/`0x06` 各回一次 `MICROPHONE_DISABLED`/`WEBCAM_DISABLED`（挡手动开关）。
**只在 WS 发**：`selkies-wr-core.js` 里没有这个分支，发过去是未知消息。

**多屏坐标的纯函数化**：`space_to_send(x, y, &space, desktop)` + `place()` +
`needs_virtual_desk()`，6 个单测。左侧屏的坑是虚拟桌面原点为负（`-1920`），
"左侧屏第一个像素 = 桌面第一个像素"这条最容易写错。整数除法的期望值要手算
（1920*65535/3839 = 32776，不是 32767）——第一次就写错在断言里。

**探针**：`ws-probe.py` 第 4 个参数指定目标屏，只统计 `PIPELINE_RESETTING` 之后的帧。
单屏机上 `display2` 实测：拿到 `PIPELINE_RESETTING display2` → 没有帧 →
`RESULT fail no frame after switching...`，服务端日志 `display 1 does not exist (1 present)`，
且 `pipeline 1: last session left, capture loop stopped`（引用计数正常，不回落主屏）。
这是**预期**结果，多屏机上同一命令应给出帧与第二块屏的尺寸。

**已知粗糙处**：请求一个不存在的屏时，采集线程会走完恢复预算（4 次重试）才报错，
这期间页面只是一个空转的加载圈。要在 acquire 失败时立刻告诉页面，得先有页面认的
"这个屏不存在"消息（现在没有），留待有真机时一起做。
