## 产物去脚本化：第一步（12 → 8 个脚本）

用户要求：最终构建产物里不要 `.cmd` / `.ps1` / `.vbs`，功能都收进 `.rs`、
打包进 `.exe`。形态选定 **方案 A**：装到用户可写目录（`%LOCALAPPDATA%\cloud-stream`
或自选路径），保持"整包自包含"。代价是「应用和功能」里不出现，卸载靠控制台或
重跑安装器。

### 这一轮做完的（commit `33f8a1c`）

**`--run`（`crates/stream-server/src/run.rs`，约 460 行）**

把整包目录布局展开成一张普通命令行，交回 `app::run` 走**同一条**路径 —— 不是
第二条启动路径。推导：`--config`（`configfile::resolve`）、`--dist`（`selkies-web`）、
`--log`（`logs\stream-server.log`）、`--tls-cert/key`（有才传）、`--upload-dir`
（`%USERPROFILE%\Desktop`）、`--auth-token`（`auth-token.txt` 第一个非空行）。
追加参数排末尾，所以 `--run --fps 60` = 原来的 `start-stream.60fps.cmd`。

单实例用命名互斥量 `Local\cloud-stream-server-instance`。不用 `Global\`（两个用户
各跑一份是合法的），不用 `tasklist`（不同目录的同名 exe 会被认成同一个）。

**`--probe`**：`--run` spawn 的短命子进程，12×2.5s 探 loopback，写
`PREFLIGHT listening on N after M probe(s)`。必须独立进程 —— `--run` 马上阻塞在
服务循环上。端口由它自己用同一套 `Config::parse` 算（所以 `--run --port 9000`
的覆盖会被看见，这是原 `probe-listen.cmd` 用 `for /f` 读参数时没有的能力）。

**GUI 子系统（`boot.rs`，约 165 行）**

`stream-server.exe` 与 `cloud-setup.exe` 都改 `#![cfg_attr(windows, windows_subsystem = "windows")]`。
这是"任务直接跑 exe 不闪黑框"的全部依据。

stdio 三种处境（**关键**）：
| 谁拉起 | 句柄 | 处理 |
|---|---|---|
| 计划任务，无控制台无重定向 | 无效 | 指到 NUL（`println!` 变成功空操作） |
| cmd / PowerShell 手动跑 | 无效 | `AttachConsole(父) + 打开 CONOUT$` |
| `Command::output()` 管道 | **有效** | 一个字都不动 |

第三行是 `--version json` 能被更新器读到的唯一原因。无条件 AttachConsole 会顶掉
管道，失败方式是"报 0.0.0"，看起来像版本号坏了。

panic 另写 `logs\crash.log`（默认输出也指向 NUL）+ 保留原 hook。

**删掉 4 个脚本**：`start-stream.cmd`(191) / `start-stream.60fps.cmd`(66) /
`run-hidden.vbs`(28) / `probe-listen.cmd`(97) = 382 行。

**产物加 `cloud-setup.exe`**：此前构建得出来但 `$LauncherNames` 里没有，于是
"四动作可视化"在真正的发布包里仍然只是那批脚本。

## 第二步：单 exe 内嵌安装器（`6b21678`）

用户拍板两件事：**单 exe 内嵌**（不给包里放第二个文件），**卸载真删目录、

### 落成的结构

| 文件 | 职责 |
|---|---|
| `crates/setup/build.rs` | `embed_manifest`（原）+ `embed_payload`：`CSPK1` 归档 + gzip → `OUT_DIR/payload.gz` |
| `crates/setup/src/pack.rs` | 读归档、`safe_rel_path`、`unpack_to`（先写 `<目标>.new` 再 merge）、`place_self`、`default_target` |
| `crates/setup/src/install.rs` | 两段流程 + 任务 XML + 防火墙 + 等端口 + `--task-xml` 诊断 |
| `crates/setup/src/report.rs` | 结论文件（与 install.cmd 同格式同路径）+ `stamp()` |
| `docs/operations-install.md` | 这一层的说明书（含"现在能验证到什么程度"表） |

### 几个决定与理由

- **角色判据是"我旁边有没有 stream-server.exe"**，不是"我是不是被双击了"
  （后者在进程内没有答案）。归档里刻意不含 cloud-setup.exe 自己，否则是
  "exe 里嵌着包含自己的包"；装完 `place_self` 复制进去，之后它就是控制台。
- **解压必须在用户令牌下**：`runas` 可能切账户，那时提权进程的
  `%LOCALAPPDATA%` 是别人的家。所以两段：用户令牌铺文件，管理员只做
  防火墙 + 任务，`--dir` 显式传过边界。
- **任务注册走 `schtasks /Create /XML`，不走 COM**（与上面记忆表里的原计划
  相反）：COM 要 ITaskService/ITaskDefinition 一整套 vtable，而 XML 是一段
  文本 —— 能 diff、能贴到另一台机器试、能被 `--task-xml` 打出来看。
  代价是要摸准 schema，见下。
- **XML 只写真实导出里出现过的元素**。先导出 `\Microsoft\Windows\*` 下几个
  任务对比：两个真实任务的 `<Settings>` 顺序并不一致（一个近乎字母序），说明
  解析器不按 xs:sequence 严格校验 —— 但为了少一处风险，还是把
  `AllowStartOnDemand`/`WakeToRun`/`RunOnlyIfIdle`/`Priority` 这些没见过的
  全删了。
- **端口问服务端自己**（`--print-config json`），不抄第二套解析。
  `open-inbound.cmd` 里"40000-40049 必须和默认值同步"那句注释就是自白。

### 本机环境坑（这轮新增）

- **`schtasks.exe` 在沙箱的程序黑名单里**（安全中心 → 命令安全 → 程序黑名单），
  任何形式都不行，也不能绕过。所以任务注册这一环在开发机上验不了。
- `netsh.exe` **没有**被拦（`show rule` 能跑）—— 意味着这里绝不能真跑
  `--finish`，它会改掉本机防火墙。
- 当前会话是**提权**的（`IsUserAnAdmin` = True），所以跑 `--install` 会直接
  进第二段，不会弹 UAC —— 也就不能用"点掉 UAC"这种方式做无副作用验证。
- `Export-ScheduledTask` / `Register-ScheduledTask`（COM，不是 exe）**能用**。
  拿它当"真解析器"验证任务 XML：注册 `MCStreamSrv-xmlcheck`（动作改指一个
  不存在的路径，万一触发也什么都不发生）→ 读属性 → 立刻注销。结果
  `Interactive / Limited / IgnoreNew / PT0S`、两个触发器、回读含 `--run`。
- 脚本里 `& .\gui.exe --flag` **拿不到 stdout**（不等 GUI 进程）。
  要取输出必须 `> file` 再读文件。
- `-CargoArgs '--features embed'` 会被当成**一个**参数传给 cargo；
  多值要 `-CargoArgs @('--features','embed')`。

## 第四步：`.150` 真机安装，装成功被报成失败（70c558e）

用户报"在 .150 安装时产生异常"，截图是"注册计划任务失败 + schtasks 说: 一串乱码"。

**现场和报错相反**：任务已创建、状态 Running、`listening on https://0.0.0.0:8080`、
日志正常。也就是说安装其实成功了。（顺带：`pack::unpack_to` 这一环也因此验收了 ——
2015 个文件真铺到了 `C:\Users\Admin\AppData\Local\cloud-stream`。）

两个独立真 bug + 一个我自己引入的回归：

1. **`from_utf8_lossy` × `contains("成功")`**：`schtasks` / `netsh` 的输出走 OEM
   代码页（中文 936/GBK），当 UTF-8 解就是 `鎴愬姛`，于是"成功"两个字根本不存在，
   退出码 0 也判成失败。改 `sys::decode`（先严格试 UTF-8 → 失败走
   `GetOEMCP()` + `MultiByteToWideChar`），并新增 `sys::run` 把**退出码**带回来，
   `create_verdict` 只看退出码。文案不可依赖（英文机 SUCCESS、中文机 成功），
   退出码不翻译。
   - 这印证了一句话：当时 `command` 的注释写着"不要指望读中文，只找 ASCII 片段"，
     而 `register_task` 违反了它。知道规矩和守住规矩是两件事。
2. **`%USERDOMAIN%` 拼账户名**：工作组机器上它是字面量 `WORKGROUP`（不是容器名），
   拼出 `WORKGROUP\admin` → Task Scheduler 答"帐户名与安全标识间无任何映射完成"。
   **只在脚本/会话里跑才露头**：双击运行时 `%USERDOMAIN%` 又是计算机名。
   改成先问 `whoami`，退路才用环境变量且遇 WORKGROUP 换 COMPUTERNAME。
3. **回归（我自己引入的）**：为让"安装 / 修复"能覆盖运行中的任务，一度把 `/End`
   无条件放在 `[3/4]` 前 —— 结果"因别的原因建不起来"会顺手停掉本来能跑的服务
   （.150 上真停过一次，1 分钟后被 TimeTrigger 拉回来）。改成 `/Create` 失败后
   才 `/End` 并重试一次。

**一个方法论上的收获**：先只修编码、不改别的，第二次安装就把第二个 bug 自己
报了出来（可读的 `(9,33):UserId:WORKGROUP\admin`）。乱码会把"多个 bug 叠在一起"
伪装成"一个 bug"。所以**先让错误可读，再改判定**，顺序不能反。

- ssh 别名 `mc-150`，账户 `Admin`，会话是 **High 完整性**（已提权），能直接建任务，
  所以 `cloud-setup.exe --install --yes --dir ...` 在那边跑不会弹 UAC。
- 成功路径会弹"安装完成"框，ssh 里没人点 → 用
  `Start-Process -PassThru` + 轮询 `%ProgramData%\cloud-stream\last-install.txt`

- 远端 PowerShell 的坑：`-EncodedCommand` 被安全策略拦（"Encoded commands hide
  the actual code"）；改用 `Get-Content x.ps1 -Raw | ssh host "powershell -NoProfile
  -Command -"`。要读 native 命令的中文输出得把 `[Console]::OutputEncoding` 设成
