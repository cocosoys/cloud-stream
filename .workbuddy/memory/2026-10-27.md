## #63 fps 归因（真机 192.168.59.148，SSH 探针实测）
- SSH 通道：`ssh -i ~/.ssh/id_ed25519_mc user@192.168.59.148`（cmd.exe，用 `cd /d` + 相对路径；**绝对路径 dir 会被吞**；`wmic` 已被 Win10.0.26200 移除，改用 ctypes 探针）。
- 部署事实：`C:\dev\stream\stream-server.exe` 由计划任务 `MCStreamSrv` 跑 `start-stream.cmd`；原脚本 `--fps 30` 且带 `--dump-frame`（每 150 帧 dump 1920x1080 BMP，被 Defender 扫描）。9:11 那次进程日志 0 字节（重启后日志正常，属历史进程歧义）。
- 硬数据（新版本 5s 自检）：`loop=56.7Hz new=9 repeat=275 skip=0 wb=275 cap_wait=8.45ms to=2.50ms conv=7.21ms enc_avg=3.4ms pipe_avg=18.9ms scale=true`。
- 三个叠加原因：
  1. `REPEAT_ENCODE_MAX=8`（我这版 #62 引入）+ DXGI 静止桌面只产 ~1.8 新帧/s → 每 5s 有 ~195 拍直接不发 → 输出塌到 ~16fps = 用户看到的 0-15。**已改回 600，输出恢复到 ~57fps（284 帧/5s），CPU 从 10% 升到 66-86% 单核。**
  2. 每拍成本超预算：采集轮询 8.5ms（scrap `would_block_if_equal` 对 6.4MB 映射表面做比较，与 timeout 无关）+ 转换 7.2ms（scalar `bgra_scale` 1718x926→1280x720 + ARGBToI420）+ 编码 3.4ms；新帧端到端 18.9ms > 16.7ms。
  3. 真 60fps 需要「采集线程与编码节拍解耦」：把 DXGI 阻塞等待放到独立线程、按最新帧投递，节拍只做 repeat/编码，理论可稳 60Hz。
- 已落地的服务端改动（commit 9f9ade9）：REPEAT_ENCODE_MAX 600、CAPTURE_TIMEOUT_FRACTION 15、默认路径免 6.4MB native 拷贝、5s 吞吐自检日志、4 个只读探针脚本、60fps 启动脚本。
- 反证：机器不缺 CPU（总忙 26%，Defender 48% 单核为干扰项），stream-server 早前只占 10% 单核即说明「根本没在干活」，不是编码器算力不够。
- 仍需浏览器端（另一 Agent 采集）：`chrome://webrtc-internals` 的 inbound-rtp video：framesPerSecond / framesReceived / framesDecoded / framesDropped / pliCount / nackCount / packetsLost / jitter / jitterBufferDelay / frameWidth-Height / bytesReceived，并需在「画面剧烈变化」时再抓一次服务端 new 计数作对照。

## #65/#66 采集线程解耦 + 60fps 验收（commit 8b03fe2）
- 问题：beat 每拍串行做 `frame()`（DXGI 8.5-11ms）+ conv + enc，60fps 的 16.7ms 预算根本不够；客户端还请求 3840x2160，把 scalar `bgra_scale` 拉到 65ms/帧。
- 改法：
  1) `capture::CaptureWorker` 独占线程内 `open_primary()`（裸 COM 指针非 Send，不能跨线程搬），单槽信箱 + ping-pong 缓冲投递最新帧；beat 用 mutex+swap 取帧；错误经信箱回传驱动原恢复链（rebuild / request_gdi / GDI 致命）；`wait_ready` 让外层先拿尺寸再开编码器。
  2) `timeBeginPeriod(1)`（main）+ `settle_beat` 混合等待（睡到截止前 1.5ms 再自旋）→ 58.2Hz 提到 60.0Hz，代价约 9% 单核。
  3) 客户端分辨率按原生收敛（`min(req, native)`，编码器打开与每拍同口径）→ 去掉 4K 上采样，scale=false、conv 65ms → 0.93ms。
  4) `--repeat-every N` 参数化 #64 补帧节流（默认 2，部署用 1）。
- 实测（1718x926 VM，客户端仍请求 4K）：`loop=60.0Hz new=9 repeat=291 skip=0 cap_wait=0.00ms conv=0.93ms enc_avg=4.7ms pipe_avg=5.7ms scale=false`，即 300 帧/5s = 60fps；CPU 83-89% 单核（4 核机的 21%）。
- 注意：本仓库同时有并行会话在改 #67 文件传输（http/mod.rs、server.rs、新增 file_transfer.rs），其未完成时整树编不过（Route::Upload 未覆盖），会同时跑 cargo 抢占 target 锁把构建拖到 10+ 分钟；本次提交只纳入我自己的 6 个文件，#67 交由该会话提交。
- 回退点：`git reset --hard 24c80b8`（#65 之前）。

## #68 光标偏移回归（#66 分辨率钳制的副作用，已修并部署）
- 现象：网页里点击位置与真正落点不符，越靠右下偏差越大（用户报「光标指针再次产生问题」）。
- 真机取证（`C:\dev\stream\logs\stream-server.log`）：`SETTINGS: manual resolution -> 3840x2160` + `client resolution 3840x2160 clamped to the native display 1718x926` + `pipeline loop started: target 1718x926`。
- 根因（链路完全对上）：
  1. 前端 selkies `_applySinkCoordinates()` 用 `sinkW = video.videoWidth`（=解码到的帧宽）换算，所以 `m,x,y` 是**实际传输帧像素**（现在 1718 宽），不是请求值。
  2. 服务端 `WinInputSink::frame_to_screen` 却除以 `StreamSettings::width()`（=未钳制的请求 3840）→ 比例 1718/3840 = 0.447，点击落在应到位置的 ~45%，误差随坐标线性放大。
  3. 该副作用由 #66 引入：`min(req, native)` 改了「送到浏览器的帧尺寸」，但没有任何地方通知输入映射。
- 修法：`StreamSettings` 新增 `out_width/out_height` + `set_output()/output()`（传输几何，与请求分离）；`run_blocking_loop` 与 `run_inner_beat` 在算出 `enc_w/enc_h` 后立即 `set_output()`；`WinInputSink::transmitted_frame()` 优先 `output()`，（0,0）时才回落请求值；`map_axis()` 改为端点对端点（0→0、frame-1→screen-1），1:1 时严格恒等。另加每会话一行 INFO `input mapping: frame AxB -> screen CxD (client requested ...)`，以后偏移问题可直接从服务端日志判定。
- 注释：三处写了大段「不要改成 width()/height()」的说明（settings.rs 模块头 / pipeline 钳制点 / win_input 的 `frame` 字段），并用单测 `transmitted_frame_prefers_output_over_request`、`output_is_never_the_requested_resolution`、`map_axis_*` 兜住回退。

## 统计面板 CPU 100% 归因（配合前端处理，后端未改）
- `stream_stats.cpu_percent` 来源：`platform/sysinfo.rs` 取 sysinfo `process(p).cpu_usage()`，
  语义是**本进程占单核百分比**（多线程可 >100）。前端 `stream-stats-view.js` 的
  `Math.min(100, latest.cpu_percent)` 把它截断在 100，且不除逻辑核数 → 4 vCPU 机器上
  面板 100% 实际是整机 25%，且看不出 100% 与 180% 的区别。
- 结构性开销（60fps 稳态）：repeat 重编码（`--repeat-every 1`，静止桌面 ~58/60 拍重编同一 YUV，
  enc 4.7-4.9ms/拍 ≈0.28 核）+ `settle_beat` 每拍 1.5ms 自旋（≈0.09 核）+ 采集线程 20ms 轮询
  每帧 6.4MB 全屏 copy/memcmp + 新帧 bgra→I420 + RTP/SRTP。画面在动时接近 1 核 = 面板 100%。
- 空闲也烧：`!handle.is_on()` 分支只 `settle_beat` 不做事，但 loop 仍 60Hz + 自旋；
  实测 148 上 video off、`new=0 repeat=0` 时进程仍 18.1% 单核（整机 4.5%，probe-top.py 10s 采样）。
- 可选的降載手段（未实施）：`VP8E_SET_STATIC_THRESHOLD` 让 libvpx 对静止帧出空帧、
  视频关闭时把节拍换成 10ms sleep、面板按逻辑核数归一。

## #70 游戏模式（全屏 + 指针锁定）两个缺陷（已修并部署）
- 症状：点「游戏模式 -- 全屏并锁定指针和键盘」后 (a) 画面没铺满；(b) 键盘正常但指针不动。
- (a) 根因：流是 `object-fit: contain`。实测客户端请求 1920x1072（aspect 1.791），服务端按 #66 钳到原生
  1718x926（1.855），浏览器把 1718x926 装进 1920x1072 的盒子 → 缩到 1920x1035，上下各 ~18px 黑边。
  流的宽高比被原生桌面钉死，只能在客户端拉伸。
  修法（前端 `selkies-web-core/lib/input.js` 的 `_applyGamingStreamBox`）：游戏模式期间给**所有 sink 元素**
  （#videoCanvas/#videoWorkerCanvas/#videoStream/#stream/.video-container video）加
  position:fixed + 100vw/100vh + max-*:none + object-fit:fill，退出按元素恢复 cssText。
  **坑**：`this.element` 只是输入覆盖层，真正画画面的是 `<video>`/canvas，只改覆盖层消不掉黑边。
  映射验证：`_sinkBox()` 在 fill 时把元素盒当画面；`_applySinkCoordinates()`（m,x,y）与
  `_pointerScale()`/`_relativeToServer()`（m2）都是 帧/盒 逐轴缩放，拉伸后仍逐轴 1:1。
- (b) 根因（服务端）：pointer lock 时前端隐藏自己的指针 + 发 `SET_NATIVE_CURSOR_RENDERING,1`，期望服务端合成。
  但 DXGI Desktop Duplication 只在**桌面内容**变化时给帧、帧内**从不含光标** → 静止桌面每拍都是 WouldBlock；
  而 WouldBlock 分支只重编码上一帧 YUV（#62），`paint_cursor` 只在「新帧」分支被调用 → 合成光标冻结。
  注入的 m2 其实移动了真实 OS 光标（这就是「键盘正常、指针不动」）。
  修法（`pipeline/mod.rs`）：每拍在取帧**之前**解析光标；新帧分支**无条件**（不受 cursor_inject 限制）保存
  `pristine_bgra` 无光标快照（因为进游戏模式时桌面往往已静止，只在 cursor_on 时快照永远拿不到底片）；
  WouldBlock 分支在 cursor_on 时用快照重绘光标 → 转 YUV → 编码（swap 进 last_yuv 保 VP8 参考链），
  绕开 --repeat-every 节流；`last_paint` 只在 位置/形状/可见性 变化时重绘，指针停住即回普通 repeat。
  cursor_inject 关闭时清 last_paint，保证再次进入第一拍必重绘。
  **不要**把快照挪回 cursor_on 分支，也不要改回「只在新帧画光标」——那就是这个 bug。
- 代价：新帧路径多一次目标尺寸 memcpy，实测 conv 0.93ms → 1.6-1.8ms（每 5s 只有 ~13-15 个新帧）。
- 自检：handover 时一行 INFO `#70 pointer handover: ... ON/OFF`；5s 统计行末尾新增 `paint=N`
  （本窗口指针驱动重绘数）。OFF = 前端没发 SET_NATIVE_CURSOR_RENDERING（客户端问题）；
  ON 且移动指针时 paint 必须增长。
- 构建注意：**Bash 工具当时整体不可用**（SandboxError 0xFFFFF826），但 PowerShell 工具可用 → 全程用 PowerShell 构建/部署。

## 被控机桌面改为 1920x1080（16:9）后的写死分辨率排查
- 结论：代码中**没有**写死分辨率。逐项核查：
  - 后端 `Config::default()` 的 1920x1080 只是 CLI 默认，`--width/--height` 可覆盖；实际 target 是
    `min(客户端请求, 原生)`，见 `pipeline/mod.rs:505/678/804`。`StreamSettings::output()` 才是输入映射的分母。
  - 前端 dashboard 的 "1920x1080" 只是分辨率下拉选项 + 翻译标签；`DPI_UNITY_ROWS=1080` 是 DPI 换算基准。
  - 前端尺寸全部来自 `videoWidth/videoHeight`、`getBoundingClientRect()`、`window.devicePixelRatio`，无固定值。
- **但发现一个真实现象（不是写死，是持久化设置）**：日志里 `SETTINGS: manual resolution -> 1920x1072` +
  `VP8 encoder opened: 1920x1072` + `scale=true`，即客户端仍处于手动分辨率模式，值为 1920x1072
  (1080 被 16 对齐成 1072，或 localStorage 残留)。后果：服务端每帧 1080→1072 双线性缩放，客户端再拉回
  1080 显示，文字发虚。这行日志只在 `manual_resolution===true` 时打印（websession.rs:757-763）。
  排查入口：设置面板「手动分辨率」关掉，或清 localStorage 的 `*_manual_width/_manual_height/_force_aligned_resolution`。
  验收信号：日志 `target 1920x1080` + 统计行 `scale=false`。
- 顺手修了上一版游戏模式铺满的时序 bug（前端 commit a8164bd）：
  `_applyGamingStreamBox` 原来用行内样式 + `if (Array.isArray(_gamingStyleBefore)) return` 的幂等守卫，
  导致 `_onFullscreenChange` 里的重施是死代码；而全屏 resize 是防抖的，`resetToWindowResolution`（自动模式，
  fill）与 `applyManualStyle`（手动模式，**contain**）会在之后重写同一批属性，黑边复活。
  改为 `<style>` 里的 `[data-selkies-gaming-fill]` 属性规则 + 全属性 `!important`，行内样式永远压不过，
  不再需要反复重施；退出只移除属性与 style，**不再回滚 cssText**（游戏模式期间核心写的行内样式才是当前想要的）。
  高度用 100% 而非 100vh（fixed 盒的 100% 不含滚动条）。
- 16:9 宿主下 contain 与 fill 等价 → 铺满不再有任何拉伸失真。
- 部署：assets `index-BJrG5dcl.js` / `selkies-core-CmBBQsQn.js` / `index-DtYiHbRm.css`，
  index.html 保留 `window.__SELKIES_STREAMING_MODE__="webrtc"`。
